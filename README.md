# AuditLine — управленческая аналитика прибыли ритейл-магазинов

AuditLine — закрытая веб-система для загрузки Excel-книг магазинов, проверки конфликтов периодов, расчета управленческих показателей и работы с доступом по отдельным торговым точкам. Система хранит факты отдельно от интерфейса, поддерживает книги за **2025** и **2026** годы, показывает аналитику по выбранному периоду и фиксирует критичные изменения в журнале и центре сигналов.

> **Важно.** Репозиторий не содержит пароли, сессии, исходные Excel-книги или другие секреты. Такие данные передаются через защищенную конфигурацию окружения и хранятся вне Git.

## Что умеет система

| Контур | Назначение |
|---|---|
| Аналитика | Сводка, месяцы, цены, расходы, остатки, профиль магазина, сравнение, портфель, сценарный пилот и дополнительный экран «Динамика». |
| Импорт Excel | Разбор `.xlsx` и `.xlsm`, предварительный просмотр, обработка конфликтов «магазин + дата», история импортов, удаление конкретного импорта и объединение переименованных точек. |
| Управление фактами | Точная запись по связке «магазин + дата + показатель», создание ручных фактов, редактирование выбранного показателя и удаление одной строки. |
| Доступ | Вход по российскому номеру телефона, роли администратора и аналитика, назначение аналитику прав «Нет / Просмотр / Изменение» по каждому магазину. |
| Контроль | Журнал существенных действий, откат поддерживаемых изменений, центр уведомлений и показ непрочитанных критичных сигналов администратору при входе. |

## Технологический стек

| Уровень | Технологии |
|---|---|
| Клиент | React 19, TypeScript, Vite, Wouter, TanStack Query, Recharts, Lucide. |
| Сервер | Express, tRPC 11, TypeScript. |
| База данных | MySQL/TiDB через Drizzle ORM. |
| Файлы | Защищенное объектное хранилище через `server/storage.ts`. |
| Разбор книг | Пакет `xlsx`; макросы не исполняются. |
| Тесты | Vitest; проверяются авторизация, матрица доступа, пороги уведомлений и разбор импорта. |

## Клиентская часть

Клиент строится вокруг `AuditShell.tsx`. Он отвечает за настольную и мобильную навигацию, выбор темы, индикатор текущего раздела, поиск магазина, кнопку возврата вверх и общий фильтр периода. Аналитические страницы не содержат собственных копий фактов: они обращаются к `useImportedAudit.ts` и `useAuditFacts.ts`, которые получают данные через `trpc.audit.dashboard`.

| Файл | Ответственность |
|---|---|
| `client/src/contexts/AuditContext.tsx` | Выбранный магазин, диапазон дат, светлая/темная тема и сохранение этих настроек в браузере. |
| `client/src/components/DateRangeControl.tsx` | Двухэтапный выбор начала и конца периода, предварительная полоса при наведении и стандартные периоды: неделя, месяц, квартал, год. |
| `client/src/components/AuditCharts.tsx` | Общие Recharts-компоненты, легенда с включением/скрытием серий и системная палитра светлого режима. |
| `client/src/pages/ImportData.tsx` | Предпросмотр и подтверждение импорта, история импортов, удаление импорта и объединение точек. |
| `client/src/pages/ManageData.tsx` | Точечное редактирование фактов по выбранной дате. |
| `client/src/pages/AccessAdmin.tsx` | Создание аккаунтов, выбор роли и тумблеры прав на магазины. |
| `client/src/pages/ControlCenter.tsx` | Дополнительный экран «Динамика»: сравнение 2026 к 2025, рейтинг изменения прибыли и контроль запаса. |

## Сервер, база данных и поток данных

### Импорт Excel

1. Администратор выбирает книгу `.xlsx` или `.xlsm` на странице импорта.
2. `server/audit.ts` читает файл в памяти и использует имя файла для определения года.
3. Первые три листа игнорируются; каждый последующий лист становится отдельным магазином.
4. Для каждого распознанного месяца система извлекает месячные итоги. Колонки сопоставляются по заголовкам, поэтому поддерживаются небольшие различия между книгами 2025 и 2026 годов.
5. Перед записью проверяется конфликт по сочетанию **магазин + дата записи**. При подтверждении можно заменить сохраненные факты или пропустить совпадающие даты.
6. Исходный файл сохраняется в защищенном хранилище, а нормализованные периоды и показатели — в БД.

> Месячные данные Excel хранятся датой первого дня месяца. Ручной факт может быть добавлен на любую дату; это позволяет корректировать конкретную запись, не меняя соседний месяц.

## Модель доступа

| Роль | Возможности |
|---|---|
| Администратор | Видит всю сеть, создает пользователей, импортирует/удаляет книги, управляет фактами, назначает доступы, смотрит журнал и сигналы. |
| Аналитик + просмотр | Видит только назначенные магазины. Изменять факты и импортировать файлы не может. |
| Аналитик + изменение | Может изменять факты только у магазинов, где тумблер установлен в «Изменение». |

Права проверяются сервером. Скрытие кнопки в интерфейсе не считается защитой: `server/accessControl.ts` также фильтрует выдачу магазинов и запрещает неразрешенные операции.

## Уведомления и журнал

Критичный сигнал создается, когда чистая прибыль становится отрицательной, либо когда существенное изменение выручки, чистой прибыли или списаний М. превышает относительный и абсолютный порог. Администраторы получают все системные сигналы; для конкретной точки получателями также становятся аналитики с назначенным доступом к ней. Непрочитанные критичные уведомления показываются администратору сразу после авторизации и остаются в разделе **«Сигналы»**.

Журнал не подменяет первичные документы: он фиксирует, кто и что изменил в системе. Откат доступен только для операций, где исходное состояние сохранено и восстановление не затронет более поздние факты.

## Локальный запуск

```bash
pnpm install
pnpm dev
```

| Команда | Назначение |
|---|---|
| `pnpm dev` | Запускает клиент и сервер в режиме разработки. |
| `pnpm check` | Проверяет TypeScript без сборки. |
| `pnpm test` | Выполняет Vitest-тесты. |
| `pnpm drizzle-kit generate` | Создает SQL-миграцию после изменения `drizzle/schema.ts`. |

Для работы требуются переменные окружения платформы, включая подключение к базе, секреты сессии и стартовый пароль администратора. Не создавайте `.env` с реальными секретами в Git и не публикуйте логины/пароли в issues, commit messages или UI.

## Правила безопасной доработки

1. При изменении схемы сначала обновляйте `drizzle/schema.ts`, генерируйте миграцию, прочитайте SQL и только затем применяйте ее.
2. Не удаляйте импорт через прямую очистку показателей: используйте операцию удаления импорта, чтобы сохранить целостность периодов и очистить пустые магазины.
3. Не заменяйте существующие аналитические страницы при добавлении новых отчетов. Новые срезы должны быть отдельными страницами или явно отделенными блоками.
4. Любое новое ограничение доступа должно быть реализовано одновременно в API и интерфейсе.
5. Перед публикацией запускайте `pnpm check`, `pnpm test`, проверяйте свежие серверные журналы и обновляйте `todo_store_permissions_notifications.md`.

## Где расширять систему дальше

Следующие улучшения логично строить поверх существующей архитектуры: автоматическое сравнение «факт–план», выгрузка управленческого PDF, интеграция уведомлений с корпоративным мессенджером, план-факт по аренде/ФОТ и сценарии оборачиваемости по категориям. Для каждого такого изменения требуется сохранить принцип: **факт остается в базе, а расчет и визуализация — воспроизводимыми**.
