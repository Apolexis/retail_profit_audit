# Аналитика Магазинов

**Аналитика Магазинов** — закрытая управленческая система для импорта Excel-книг торговых точек, анализа прибыли, расходов, товарного запаса и сценариев улучшения экономики. Система разделяет исходные факты, аналитические расчеты и права доступа, поэтому пользователь видит только разрешенные магазины, а значимые действия остаются в аудиторском следе.

> **Безопасность.** В репозитории нет исходных Excel-книг, паролей, токенов или сессий. Конфиденциальные значения передаются через защищенную конфигурацию окружения и не должны попадать в Git, логи или интерфейс.

## Возможности

| Контур | Что реализовано |
|---|---|
| Аналитика | Сводка, сравнение месяцев, цены, расходы, остатки, профиль магазина, портфель, сравнение магазинов, динамика периодов и сценарный центр «Пилот». |
| Периоды | Единый двухэтапный календарь на аналитических страницах: первый клик задает начало, второй — конец. Есть стандартные интервалы, включая «С начала этого года» до текущей локальной даты пользователя. |
| Импорт Excel | Поддержка `.xlsx` и `.xlsm`, просмотр до записи, конфликты «магазин + дата», замена или пропуск, история, удаление конкретного импорта и ручное объединение переименованных точек. |
| Факты | Редактирование по связке **магазин + точная дата + показатель**, добавление и удаление отдельных записей, а также скрытие факта из расчетов без удаления из базы. |
| Доступ | Вход по российскому мобильному номеру, роли администратора и аналитика, тумблеры «Нет / Просмотр / Изменение» по каждому магазину. |
| Контроль | Центр сигналов, переход к первоисточнику события, подробный журнал «до → после» и безопасный откат поддерживаемых изменений. |
| Отчеты | Еженедельная управленческая сводка для администраторов за предыдущую календарную неделю. День и время по Москве настраиваются в интерфейсе. |

## Аналитические разделы

| Раздел | Управленческий вопрос | Ключевые срезы |
|---|---|---|
| Сводка | Какова экономика сети и конкретной точки? | Выручка, чистая прибыль, маржа, сезонность, навигация в дочерние разделы. |
| Месяцы | Где и когда изменилась динамика? | Показатель по месяцам, сетевой срез и точка, общий календарный период. |
| Цены | Как соотносятся закупки и продажи Коп./Мор.? | Общий товарный поток и отдельные категории по магазинам. |
| Расходы | Какие статьи требуют управленческой проверки? | Суммы, доля в выручке, сетевые медианы и сигналы отклонения. |
| Остатки | Сколько денег находится в товаре и каков риск запаса? | Покрытие в днях, **медиана покрытия сети**, остатки на начало/конец, изменение, перемещения, уценка и списания. |
| Динамика | Как сопоставить разные годы и произвольные интервалы? | Независимый основной и сравнительный периоды, поэтому раздел готов к будущим импортам 2027+ без переработки. |
| Пилот | Как оценить эффект управленческой гипотезы? | Режим одной точки или сети; цена, объем, общая закупочная цена, закупочная цена Коп., закупочная цена Мор., списания, расходы и запас. |
| Еженедельные отчеты | Что руководителю проверить по итогам прошлой недели? | Последний доступный P&L-срез, топ прибыли, риски, количество действий и история отчетов. |

## Импорт и данные

### Правила разбора Excel

1. Год определяется по имени загружаемого файла.
2. Первые три листа считаются техническими и пропускаются.
3. Каждый лист, начиная с четвертого, считается отдельным магазином.
4. Распознаются заполненные месяцы и их итоговые показатели.
5. При совпадении **магазина и даты** администратор выбирает замену существующих фактов или пропуск совпадений.
6. Новый или переименованный лист образует отдельную точку. Если это тот же магазин, объедините точки через страницу импорта и выберите правило обработки совпадающих дат.

Месячные данные, пришедшие из книги, хранятся датой первого числа соответствующего месяца. Ручные факты можно создать на любую дату. При выборе дня в редакторе система показывает импортную месячную запись того же месяца, если для выбранного дня отдельного ручного факта еще нет.

## Доступ, сигналы и журнал

| Роль/уровень | Возможности |
|---|---|
| Администратор | Вся сеть, импорты, факты, пользователи, доступы, сигналы, журнал и недельные отчеты. |
| Аналитик — просмотр | Только назначенные магазины, без изменения фактов или загрузки книг. |
| Аналитик — изменение | Факты только тех магазинов, где выбран тумблер «Изменение». |

Защита реализована в API, а не только скрытием кнопок. Для сигналов доступны прямые переходы к первоисточнику. Критичные уведомления видит администратор при входе; для магазина они также могут быть получены аналитиком с назначенным доступом. Журнал фиксирует, в том числе, импорты, удаление, объединение, права, видимость магазина/факта и изменение метрик. Откат доступен только там, где исходное состояние позволяет выполнить безопасное восстановление.

## Еженедельный отчет

Еженедельная сводка формируется за **предыдущую календарную неделю**. В настройках раздела «Еженедельные отчеты» администратор выбирает день недели и время **по Москве**. Устойчивый серверный запуск выполняется через платформенный Heartbeat, не зависит от открытого браузера и защищен проверкой доверенного запуска.

В отчете показаны выручка, чистая прибыль, маржа, количество точек, убыточные магазины, действия за неделю, лидеры прибыли и точки риска. P&L-часть строится по последнему доступному импортированному месяцу; это явно раскрывается в методологии каждого отчета.

## Локальная разработка

```bash
pnpm install
pnpm dev
```

| Команда | Назначение |
|---|---|
| `pnpm dev` | Запускает клиент и сервер в режиме разработки. |
| `pnpm check` | Проверяет типы TypeScript. |
| `pnpm test` | Запускает Vitest-тесты. |
| `pnpm drizzle-kit generate` | Создает SQL-миграцию после изменения `drizzle/schema.ts`. |

Для разработки требуются переменные окружения платформы для подключения к БД, серверных сессий и защищенного хранилища. Не создавайте `.env` с реальными значениями в Git.

## Правила безопасной доработки

1. При изменении схемы обновите `drizzle/schema.ts`, сгенерируйте миграцию, прочитайте SQL и только затем применяйте ее.
2. Удаляйте книгу только через операцию удаления импорта, а не прямой очисткой метрик: это сохраняет целостность периодов и удаляет пустые магазины корректно.
3. Не заменяйте действующие страницы новыми срезами без прямого решения: новые управленческие блоки добавляйте отдельным экраном или явно отделенным разделом.
4. Любое правило доступа реализуйте одновременно в серверной проверке и интерфейсе.
5. Перед публикацией запускайте `pnpm check`, `pnpm test`, проверяйте свежие журналы сервера и актуализируйте `todo_store_permissions_notifications.md`.

## Возможные следующие улучшения

Логичное развитие системы — отдельный контур **план‑факт** по выручке, прибыли, аренде и ФОТ; выгрузка недели в PDF; канал корпоративного мессенджера для критических сигналов; анализ оборачиваемости по товарным категориям. Для любого нового модуля сохраняйте главный принцип: **факт неизменяемо хранится в базе, а выводы и визуализации должны быть воспроизводимы из него**.
