# Лояльность и конструктор нефискального блока чека Эвотор

**Статус:** будущий отдельный кассовый контур. Документ не запускает приложение на терминалах, не создает клиентов, бонусы, скидки или печать на реальных кассах.

## 1. Что подтверждено технически

Облачный API Эвотора подходит для аналитического получения магазинов, терминалов, номенклатуры и документов, но кассовое взаимодействие со сканером и печатью требует приложения, установленного на смарт-терминал. Для приложения на терминале Эвотор документирует печать произвольных данных в чеке через `IntegrationService` и разрешение `ru.evotor.permission.receipt.printExtra.SET`; оно может передать текст, штрихкод или изображение и указать область печати.[1] [2]

| Возможность | Подтвержденный путь | Ограничение текущего проекта |
| --- | --- | --- |
| Карта лояльности по штрихкоду | Готовый сервис Эвотор.Маркета либо собственное приложение на терминале | Обычный облачный read-only доступ этого не выполняет |
| Начисление/списание бонусов | Кассовый модуль должен получить ID клиента до оплаты и вернуть правило бонусов | Нельзя применять скидку или бонус без отдельного кассового сценария и теста |
| Текст/акция на чеке | Терминальное приложение через `printExtra` | Только добавляемый нефискальный блок |
| Штрихкод на чеке | `PrintableBarcode` в терминальном приложении | Тип кода и читаемость проверяются на конкретном принтере |
| QR-код | `PrintableBarcode.BarcodeType.QR_CODE` в терминальном SDK | Физическую читаемость и длину ленты обязательно проверить на используемых моделях терминалов |

## 2. Карта клиента на кассе

### Рекомендуемый порядок

Кассир не сканирует карту клиента в обычный поток добавления товара. На терминале открывается явное действие **«Карта клиента»**: оно принимает штрихкод/номер телефона, отправляет на сервер только идентификатор карты, получает клиента и доступный бонусный сценарий, а затем возвращает кассира к оплате. После закрытия чека сервер создает неизменяемую операцию начисления/списания, связанную с чеком и магазином.

Это исключает ошибку, при которой карта принимается за товарный штрихкод. При отсутствии связи с сервером касса должна либо работать без бонусов, либо использовать заранее утвержденный безопасный offline-режим; начислять бонусы «на глаз» нельзя.

### Варианты запуска

| Вариант | Преимущество | Компромисс |
| --- | --- | --- |
| Готовый сервис Эвотор.Маркета | Быстрый запуск: опубликованные решения поддерживают поиск по карте/телефону, бонусы и печать информации о них на чеке.[3] | Данные клиентов и правила находятся у стороннего сервиса; нужно отдельно проверить экспорт, API, тариф и обработку персональных данных |
| Собственное приложение Эвотор + сервер «Рыбного» | Единые карта, Wallet, бонусы, предложения и аналитика в собственном контуре | Требуются APK-приложение, тестирование на терминалах, публикация/развертывание и отдельная защита персональных данных |

Первый безопасный шаг — не разработка, а решение владельца: готовый сервис либо собственный контур. До этого карточка лояльности не смешивается с товарным учетом и журналом продавца.

## 3. Конструктор нефискального блока чека

Конструктор управляет только добавляемыми элементами вокруг/внутри разрешенной области печати. Он **не** получает права менять товары, количество, цену, скидку, НДС, оплату, обязательные реквизиты или итог фискального чека.

| Настройка шаблона | Пример |
| --- | --- |
| Название и состояние | `Сентябрьская акция`, черновик/опубликован/архив |
| Область печати | Верх или разрешенная нижняя область, подтвержденная терминальным тестом |
| Блоки | Короткий текст, промокод, штрихкод, QR-код, изображение |
| Компактность | Максимум строк, обрезка с явным preview, один короткий CTA вместо длинного описания; ширина и число символов строки берутся из API встроенного принтера |
| Назначение | Все магазины, выбранные магазины, период акции, условие наличия карты лояльности |
| Версия | Неизменяемая версия публикуемого шаблона и возможность повторить вид исторического чека |

Перед публикацией администратор видит preview на типовой узкой чековой ленте и расчетное число добавляемых строк. Если текст не помещается, шаблон не публикуется до сокращения; приложение не должно самовольно уменьшать шрифт до нечитаемого размера.

## 4. Доступ, аудит и данные клиентов

Настраивать и публиковать шаблоны может только администратор. Руководитель может видеть результаты и, при отдельном праве, создавать черновик без публикации. Журнал фиксирует автора, время, магазин/период назначения и изменение версии шаблона, но не хранит полный код карты, номер телефона или содержимое персональных предложений.

Клиенты, согласия, телефоны, история начислений и балансы находятся в отдельном контуре лояльности. До запуска требуется проверить модель обработки персональных данных с ответственным специалистом; товарные права продавца и финансовые данные с этим контуром не смешиваются.

## 5. Порядок будущего пилота

1. Выбрать готовый сервис или собственное терминальное приложение.
2. Подтвердить список терминалов и создать тестовую версию приложения для них.
3. Проверить на тестовой кассе: скан карты не добавляет товар, бонус не меняет чек вне заданного правила, а печатный блок не повреждает обязательную часть чека.
4. Утвердить короткие шаблоны акции/промокода и проверить физическую длину ленты.
5. Запустить один магазин, сверить чеки и операции лояльности, затем принимать решение о сети.
