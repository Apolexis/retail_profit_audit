> **Статус:** архивная фиксация безопасной диагностики 17.09.2026. В Эвотор, кассы, товары, чеки, пользователей и базу приложения ничего не записывалось. Токен, названия товаров, суммы, номера чеков, контакты покупателей и коды маркировки в этот документ не попадают. Целевой контракт — Эвотор Cloud API V2, см. [`evotor_v2_contract_research.md`](./evotor_v2_contract_research.md); этот документ не разрешает использование V1 в новой реализации.

## Фактические единицы и дробность

Read-only проверка каталога одной точки вернула 816 сущностей. Во всех есть идентификатор, код и штрихкод; у 812 указана единица. В данных встречаются две исходные единицы: `дроб` и `шт`. Поле `measurePrecision`, которое предусматривается контрактом товара, в фактическом V2-ответе не пришло, поэтому его нельзя подменять постоянным значением.

| Наблюдение в строках продаж за 30 дней | Количество | Решение для внутреннего регистра |
|---|---:|---|
| `дроб` | 2 127 строк | Сохранять исходную единицу и точность; после подтвержденного маппинга в пользовательском интерфейсе показывать `кг`, не меняя исходный ответ Эвотор. |
| `шт` | 733 строки | Учитывать как штучный товар; дробность не применять, если 1С и карточка товара не допускают иное. |
| Единица не указана | 1 строка | Не проводить автоматическое сопоставление; отправлять в очередь сверки. |
| Количество с 3 знаками после точки | 1 704 строк | Хранить количество с точностью не ниже `0.001`. |
| Количество с 2 знаками после точки | 317 строк | Не округлять до целого при импорте. |

Следовательно, весовой контур поддерживается фактическими данными. По решению владельца техническое значение `дроб` отображается пользователю как `кг`; это обозначение применяется только после подтвержденного маппинга товара и не меняет исходное поле, количество или точность в интеграционном контуре.

## Что можно построить на этих данных

Слой фактических продаж сможет считать для сети, магазина, категории и товара: число чеков, выручку, средний чек, количество или вес, среднюю фактическую цену, скидки при наличии соответствующей транзакции, возвраты по документам `PAYBACK`, а также рейтинг позиций. Эти показатели будут фактом из Эвотора и не изменяют финансовую таблицу.

Валовая прибыль будет рассчитываться только после связки строки продажи с версионной закупочной себестоимостью 1С. Поле себестоимости, которое приходит из Эвотора, сохраняется для сверки и диагностики, но не подменяет установленный источник истины — 1С.

## Архивный маршрут V1, использованный только для диагностики

Для фактической диагностики использовался документированный маршрут `GET /api/v1/inventories/stores/{storeUuid}/documents` с серверным заголовком `X-Authorization`. В нем применялись `types=SELL,PAYBACK`, `gtCloseDate` и `ltCloseDate`; один диапазон не больше месяца. Историческая V1-справка содержала утверждение о документах не старше шести месяцев.[1] Это **не доказательство лимита API V2**, не правило хранения Эвотор в целом и не основание проектировать новый импорт на V1.

| Правило реализации | Причина |
|---|---|
| Не переносить V1-месячные фильтры в V2 без подтверждения | У V2 официально подтверждены endpoint и `cursor`, но не опубликован на доступной странице набор фильтров периода/типов. |
| Использовать уникальный ID документа и тип транзакции как ключ идемпотентности | Один и тот же чек может быть снова доступен при повторной выгрузке. |
| Связывать товарную строку с внутренней номенклатурой через штрихкод, затем подтверждать вручную конфликтные случаи | В проверенных строках отсутствует стабильный `positionId`, но штрихкод присутствует. |
| Помещать строки без единицы, без сопоставления с товаром или с конфликтом штрихкода в очередь сверки | Нельзя автоматически объединять неоднозначные товары по названию. |
| Не считать товарный остаток по одному Эвотору | Остатки магазинов ведутся внутренним регистром: начальный срез/инвентаризация, накладные 1С, продажи, списания, возвраты и подтвержденные преобразования. |

## Ограничения до реализации

Публичная документация разделяет V1 и V2; V2 использует `next_cursor`, но точные фильтры периода/типов на доступной публичной странице не раскрыты. Поэтому первый модуль **не использует V1**: его проектирование останавливается до подтверждения V2-контракта, а не подменяет его V1-маршрутом.

Текущая проверка выполнена для одной точки и служит подтверждением доступности, а не загрузкой всей сети. Перед включением регулярной синхронизации нужны: список сопоставлений 40 точек, документированная стратегия повторов/лимитов, витрина ошибок, отдельное разрешение на периодические запросы и проверка возвратов `PAYBACK`.

## Следующий безопасный этап

1. Получить preview каталога Эвотора по всем точкам: только UUID, группа, код, штрихкоды, единица и точность — без создания товаров.
2. Загрузить тестовый файл выгрузки 1С в preview и сформировать экран сопоставлений «1С ↔ Эвотор ↔ внутренний товар».
3. До включения начальной загрузки продаж получить от поддержки Эвотор или актуальной V2 OpenAPI официальное подтверждение максимально доступной глубины истории и допустимого фильтра периода.
4. Отдельным согласованием включить регулярное обновление продаж. Каждый запуск и его результат фиксируются в существующем общем журнале.

## Реализованный preview и подтверждение каталога — 18.09.2026

В административном экране «Инвентаризации» добавлен **read-only preview** номенклатуры через Эвотор Cloud API V2. Сервер использует только `GET /stores` и `GET /stores/{store-id}/products` с V2 media type и Bearer-токеном из server-only environment. Экран берет магазин Эвотор исключительно из сохраненного соответствия выбранной внутренней точки: произвольно выбрать другую кассу нельзя. Администратор видит первые 40 позиций, может найти позицию по названию, коду или штрихкоду и раскрыть следующую порцию. В preview показываются только идентификатор, имя, код, число штрихкодов, исходная единица (техническое `дроб` отображается как `кг`) и НДС-признак.

> Preview **не создает и не изменяет** внутренние товары, цены, себестоимость, остатки, связи, историю инвентаризаций или объекты Эвотор. Цена и `cost_price` намеренно не передаются в UI preview.

После прямого разрешения владельца реализована кнопка подтверждения preview. Она создает или обновляет только изолированные карточки `операционный магазин + Evotor product ID`: ID, код, имя, штрихкоды, единица и НДС. Поле «Себестоимость Эвотор» принудительно сохраняется как `0` и не показывается; администратор отдельно задает внутреннюю себестоимость с записью в существующий общий аудит. Никакой обратной записи в Эвотор нет.

Сохранение не выполняется, если соответствие внутренней точки и магазина Эвотор не уникально. Для такой точки нужен точный **Evotor store ID** или **terminal UUID**; выбор по совпадающему имени запрещен.

Проверка защищенного server-side доступа прошла без вывода токена или товарных данных: список магазинов и каталог выбранной точки доступны; у выбранной точки получен preview из 816 позиций. Никакой ответ Эвотор не был сохранен без нажатия отдельного подтверждения администратором.
