# Read-only инвентаризация Эвотор — 17.09.2026

> **Статус:** выполнено только безопасное чтение через серверную переменную. В Эвотор, кассы, товары, чеки, пользователей и базу приложения ничего не записывалось. Токен, названия товаров, суммы, номера чеков, контакты покупателей и коды маркировки в этот документ не попадают.

## Фактические единицы и дробность

Read-only проверка каталога одной точки вернула 816 сущностей. Во всех есть идентификатор, код и штрихкод; у 812 указана единица. В данных встречаются две исходные единицы: `дроб` и `шт`. Поле `measurePrecision`, которое предусматривается контрактом товара, в фактическом V2-ответе не пришло, поэтому его нельзя подменять постоянным значением.

| Наблюдение в строках продаж за 30 дней | Количество | Решение для внутреннего регистра |
|---|---:|---|
| `дроб` | 2 127 строк | Сохранять исходную единицу; после сопоставления с 1С явно определить бизнес-смысл и базовую единицу конкретного товара. |
| `шт` | 733 строки | Учитывать как штучный товар; дробность не применять, если 1С и карточка товара не допускают иное. |
| Единица не указана | 1 строка | Не проводить автоматическое сопоставление; отправлять в очередь сверки. |
| Количество с 3 знаками после точки | 1 704 строк | Хранить количество с точностью не ниже `0.001`. |
| Количество с 2 знаками после точки | 317 строк | Не округлять до целого при импорте. |

Следовательно, весовой контур поддерживается фактическими данными, но нет основания автоматически считать каждую строку `дроб` килограммами: окончательное соответствие единицы будет задаваться по карточке 1С и подтвержденному маппингу товара, а исходное значение Эвотора сохраняется для трассировки.

## Что можно построить на этих данных

Слой фактических продаж сможет считать для сети, магазина, категории и товара: число чеков, выручку, средний чек, количество или вес, среднюю фактическую цену, скидки при наличии соответствующей транзакции, возвраты по документам `PAYBACK`, а также рейтинг позиций. Эти показатели будут фактом из Эвотора и не изменяют финансовую таблицу.

Валовая прибыль будет рассчитываться только после связки строки продажи с версионной закупочной себестоимостью 1С. Поле себестоимости, которое приходит из Эвотора, сохраняется для сверки и диагностики, но не подменяет установленный источник истины — 1С.

## Подтвержденный маршрут чтения

Для фактической проверки использован документированный маршрут `GET /api/v1/inventories/stores/{storeUuid}/documents` с серверным заголовком `X-Authorization`. Запросу задаются `types=SELL,PAYBACK`, `gtCloseDate` и `ltCloseDate`; один диапазон не больше месяца. Официальный справочник указывает, что облако предоставляет документы, созданные не более шести месяцев от момента запроса.[1]

| Правило реализации | Причина |
|---|---|
| Загружать месяц за месяцем и хранить курсор/границу успешной загрузки | Один запрос не должен превышать месяц; повторный запуск не должен дублировать чеки. |
| Использовать уникальный ID документа и тип транзакции как ключ идемпотентности | Один и тот же чек может быть снова доступен при повторной выгрузке. |
| Связывать товарную строку с внутренней номенклатурой через штрихкод, затем подтверждать вручную конфликтные случаи | В проверенных строках отсутствует стабильный `positionId`, но штрихкод присутствует. |
| Помещать строки без единицы, без сопоставления с товаром или с конфликтом штрихкода в очередь сверки | Нельзя автоматически объединять неоднозначные товары по названию. |
| Не считать товарный остаток по одному Эвотору | Остатки магазинов ведутся внутренним регистром: начальный срез/инвентаризация, накладные 1С, продажи, списания, возвраты и подтвержденные преобразования. |

## Ограничения до реализации

Публичная документация разделяет V1 и V2; в текущем фактическом V2-ответе встречается `next_cursor`, но диапазонные V1-параметры там не применились. Поэтому первый модуль использует подтвержденный V1 read-only маршрут с месячными окнами. Детальный V2-маршрут не предполагается и не будет выдуман до отдельной технической проверки.

Текущая проверка выполнена для одной точки и служит подтверждением доступности, а не загрузкой всей сети. Перед включением регулярной синхронизации нужны: список сопоставлений 40 точек, документированная стратегия повторов/лимитов, витрина ошибок, отдельное разрешение на периодические запросы и проверка возвратов `PAYBACK`.

## Следующий безопасный этап

1. Получить preview каталога Эвотора по всем точкам: только UUID, группа, код, штрихкоды, единица и точность — без создания товаров.
2. Загрузить тестовый файл выгрузки 1С в preview и сформировать экран сопоставлений «1С ↔ Эвотор ↔ внутренний товар».
3. Только после вашего отдельного подтверждения включить начальную загрузку продаж за доступные шесть месяцев в изолированные товарные таблицы.
4. Отдельным согласованием включить регулярное обновление продаж. Каждый запуск и его результат фиксируются в существующем общем журнале.
