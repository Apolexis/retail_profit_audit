# ТЗ: ручной импорт УПД и маркировки из бухгалтерии / ЭДО

**Статус:** проектное ТЗ ручного импорта УПД. Бухгалтерия передает файл, а администратор загружает его в защищенный preview приложения. Автоматический обмен с бухгалтерией/ЭДО не строится. Импорт не должен создавать, проводить, подписывать, корректировать или отправлять документы в 1С, ЭДО, Честный ЗНАК, Эвотор или кассу.

## 1. Цель

Нужно вручную загружать в «Аналитику „Рыбный“» подтвержденные УПД по поступлениям, чтобы дополнить корректные закупки и себестоимость из 1С документной детализацией: приемкой, партией, сроками годности и индивидуальными кодами маркировки, если они есть в файле. УПД **не заменяет** закупочную цену и себестоимость 1С; он проверяет и уточняет связь документа с товаром и входящей маркированной единицей.

> Для маркированных товаров ЭДО используется для передачи сведений о движении маркированной продукции: продавец формирует УПД, покупатель сверяет его с фактическим поступлением и подписывает при отсутствии расхождений. [1]

## 2. Границы работ

| Разрешено | Не входит в задачу |
| --- | --- |
| Вручную загрузить исходный файл подписанного УПД, строки, партии, сроки и доступные коды маркировки | Проводить или корректировать документ в 1С/ЭДО |
| Связать строку УПД с документом закупки/номенклатурой 1С | Менять закупочную себестоимость, складской остаток или статус УПД |
| Передать отмены, исправления и корректировки как новые события | Создавать перемещения, продажи, списания, заявки или кассовые действия |
| Разобрать поддерживаемый XML УПД, XLSX/CSV-выгрузку или иной согласованный структурированный файл в preview | Передавать персональные данные покупателей, пароли, токены, УКЭП или ключи ЭДО |

**Источник истины:** закупки и себестоимость — корректные данные 1С. УПД бухгалтерии/ЭДО — документное подтверждение приемки и источник детализации маркировки, если такая детализация технически доступна.

## 3. Формат ручного импорта

Администратор выбирает исходный файл УПД, приложение выполняет preview и показывает распознанные документ, строки, партии, сроки и доступные марки до применения. Предпочтительны структурированный XML УПД или XLSX/CSV с тремя логическими наборами: `edi_upd`, `edi_upd_lines`, `edi_marking_units`. PDF можно хранить как исходный документ, но его структурное извлечение и наличие кодов маркировки требуют отдельной проверки на реальном образце.

Если файл имеет структурированный экспорт, он содержит `schema_version`, `source_system`, уникальный `batch_id`, `generated_at` в UTC, `business_timezone=Europe/Moscow`, режим `snapshot` или `delta` и список записей. Повторный импорт одинакового `batch_id` не должен создать дубли. Для исходного XML, где этих полей нет, приложение создает технический fingerprint файла и показывает его до подтверждения.

## 4. Обязательные данные УПД

### 4.1 Заголовок УПД: `edi_upd`

| Поле | Формат | Обязательно | Правило |
| --- | --- | --- | --- |
| `upd_id` | string | Да | Стабильный ID УПД в бухгалтерии/ЭДО; не меняется после переименования контрагента |
| `document_number` | string | Да | Видимый номер УПД |
| `issued_at` | RFC 3339 UTC | Да | Время формирования/выставления УПД |
| `accepted_at` | RFC 3339 UTC/null | Да | Время принятия покупателем; до подтверждения — `null` |
| `status` | enum | Да | `draft`, `signed_by_seller`, `accepted`, `corrected`, `cancelled` |
| `supplier_reference` | string | Да | Стабильный код/ID поставщика в 1С или ЭДО |
| `receipt_location_code` | string | Да | Код локации приемки: например `BM` или `SRS` |
| `source_purchase_document_id` | string/null | Нет | Ссылка на документ закупки 1С для сверки |
| `replaces_upd_id` | string/null | Нет | ID исходного УПД при исправлении/корректировке |
| `cancel_reason` | string/null | Нет | Причина отмены/аннулирования, если передается источником |

В приложение попадают для складской детализации только УПД со статусом `accepted`. Черновые, подписанные только продавцом, отмененные и исправленные документы передаются для истории/сверки, но не должны тихо менять ранее принятые события.

### 4.2 Строки УПД: `edi_upd_lines`

| Поле | Формат | Обязательно | Правило |
| --- | --- | --- | --- |
| `line_id` | string | Да | Стабильный ID строки УПД |
| `upd_id` | string | Да | Ссылка на заголовок УПД |
| `product_source_id` | string | Да | Стабильный ID номенклатуры 1С; не передавать только название |
| `sku` | string | Да | Артикул/код 1С для контроля маппинга |
| `name` | string | Да | Наименование для preview и сверки человеком |
| `quantity` | number | Да | Количество в базовой единице; дробная часть — через точку |
| `base_unit` | enum/string | Да | Фактическая единица: `piece`, `kg`, `g`, `l`, `ml` или согласованный код |
| `unit_price` | number | Да | Цена за базовую единицу из УПД |
| `line_total` | number | Да | Итог строки без округления интерфейса |
| `vat_rate` | number/null | Нет | Ставка НДС |
| `source_purchase_line_id` | string/null | Нет | Ссылка на строку закупочного документа 1С для сверки |
| `batch_ref` | string/null | Нет | Номер партии/серии, если ведется |
| `manufactured_at` | `YYYY-MM-DD`/null | Нет | Дата изготовления, если доступна |
| `expiry_date` | `YYYY-MM-DD`/null | Нет | Срок годности, если доступен |

### 4.3 Маркированные единицы: `edi_marking_units`

Этот набор извлекается только если выбранный вручную файл УПД реально содержит индивидуальные коды. Отсутствие таких строк **не блокирует** товарный остаток и продажу через Эвотор: это означает только, что марка еще не известна внутреннему реестру.

| Поле | Формат | Обязательно | Правило |
| --- | --- | --- | --- |
| `marking_unit_id` | protected string | Да | Исходный код маркировки передается только защищенным каналом; не выводится в обычном UI, общем журнале или логах |
| `upd_id`, `line_id` | string | Да | Ссылка на УПД и строку товара |
| `product_source_id` | string | Да | Товар 1С, к которому относится марка |
| `status` | enum/string | Да | Технический статус, который дает источник; без самостоятельной интерпретации |
| `batch_ref`, `expiry_date` | string/date/null | Нет | Если код связан с партией/сроком |
| `source_marking_record_id` | string/null | Нет | Стабильный технический ID записи источника, если есть |

## 5. Правила сопоставления и корректировок

Приложение сопоставляет УПД с 1С по стабильным ID документа, строки и номенклатуры; совпадения только по названию недостаточно. Код `receipt_location_code` должен однозначно указывать БМ или СРС. Если локация, товар, единица или количество не проходят проверку, запись попадает в preview/очередь сверки и не меняет складской факт автоматически.

Исправленный или отмененный УПД не удаляет историю. Разработчик передает новый документ/событие со статусом `corrected` или `cancelled` и с `replaces_upd_id`. В приложении появляется понятное расхождение и связь с первичным документом; себестоимость 1С не переписывается УПД.

Когда Эвотор в чеке передает конкретный сканированный код маркировки, приложение связывает чек с `marking_unit_id` и отмечает эту единицу как проданную **в магазине чека**. Накладная на магазин не назначает марку заранее. Если кода пока нет в вручную импортированном реестре УПД, продажа все равно учитывается по товару и не блокирует кассу; код попадает в очередь сверки. После позднего ручного импорта УПД связь дозаполняется отдельным аудируемым событием.

## 6. Безопасность и аудит

Коды маркировки, файлы УПД, учетные данные ЭДО, токены и УКЭП не должны попадать в клиентское приложение, общий журнал, текст ошибок или выгрузки для обычных пользователей. Их хранение и обработка допускаются только на защищенном серверном контуре. Общий журнал фиксирует сам факт импорта, число документов/строк, статусы, расхождения и исполнителя, но не значение маркировочного кода.

## 7. Первый приемочный пакет

Для preview без сохранения достаточно предоставить:

1. Один файл принятого УПД с 2–5 строками, включая хотя бы одну маркированную и одну немаркированную позицию, если такие данные доступны.
2. Ссылку этого УПД хотя бы на один документ/строку закупки 1С.
3. Один пример корректировки или отмены, если бухгалтерия/ЭДО умеет его выгружать.
4. Подтверждение, содержит ли выбранный тип файла УПД коды маркировки или к нему нужен отдельный структурированный файл/выгрузка.

Пакет сначала разбирается только в preview. Реальные данные, партии и марки не сохраняются до отдельного явного подтверждения владельца.

## 8. Что нужно подтвердить разработчику

| Вопрос | Требуемый ответ |
| --- | --- |
| Источник УПД | Какая система/оператор формирует файл, который вручную загрузит администратор |
| Формат | XML УПД, XLSX, CSV или иной согласованный структурированный файл; автоматический API не нужен |
| Уникальные ключи | Какие ID УПД, строк, номенклатуры, закупок и маркированных единиц стабильны |
| Маркировка | Передаются ли отдельные коды, их статусы, связь с УПД/строкой/партией и когда они появляются |
| Сопоставление 1С | Как `source_purchase_document_id` и `source_purchase_line_id` связываются с текущими закупками/себестоимостью 1С |
| Корректировки | Какими статусами и ссылками передаются УПДи/УКД/отмены |
| Безопасность | Какой защищенный канал и сервисная учетная запись будут использоваться; значения ключей не передаются в переписке |
