# Спецификация операционного реестра «Выручка» магазинов

**Статус:** V1 реализована 17.09.2026. Реестр собирает ежедневную операционную передачу выручки магазина и **не изменяет** финансовые факты, старый финансовый Excel-импорт, финансовые права, сессии или расчет прибыли. Это не кассовая команда Эвотор и не синхронизация с кассой. Последующие расширения выполняются только по этому контракту.

> Смысл записи: наличные, которые сдаются за день, плюс безналичные оплаты и все наличные расходы за день дают операционную сумму, которую магазин фактически наторговал. Эта сумма может не совпасть с кассовой суммой из-за оставленного размена, времени закрытия дня, возвратов и других причин. Расхождение не исправляется автоматически.

## 1. Область доступа и активная запись

Одна активная запись относится к одному операционному магазину и одной бизнес-дате `Europe/Moscow`. Для пары «магазин + дата» допускается одна активная запись. Продавец видит только пять последних **собственных** записей по своей точке и вправе только создать новую; просмотр, изменение и удаление чужих записей сервером запрещены.

Администратор видит реестр всех магазинов **за одну выбранную дату**, создает запись с явным выбором магазина, изменяет существующую запись и печатает результат. Удаление из рабочего реестра доступно только администратору и требует причину. Оно не уничтожает исходные данные: запись помечается удаленной, исчезает из рабочего реестра, а исходная и удаляющая версии остаются в истории и общем журнале. После этого за ту же пару «магазин + дата» можно создать новую активную передачу; она восстанавливает запись следующей версией, не создавая дубликат.

### 1.1 Вход магазина и первичный пароль

Продавец входит только через отмеченный режим **«Вход для магазинов»** с выданными логином и паролем. В этом режиме телефонное поле заменяется полем логина, а быстрый вход с ключом доступа не показывается и серверно запрещен. Администратор и аналитик продолжают входить по российскому номеру телефона; произвольный логин не может быть присвоен этим ролям.

Начальный пароль магазина допустим только для первого входа. После него до смены на пароль длиной не менее десяти символов доступны только страница профиля и форма изменения пароля. Сам пароль не выводится, не попадает в общий журнал и не хранится в документации. Создание учетной записи, назначение магазина и сброс пароля журналируются существующей функцией `recordChange` без значения пароля.

| Роль | Создать | Просмотреть | Изменить | Удалить из рабочего реестра | Печать |
| --- | --- | --- | --- | --- | --- |
| Продавец | Только за назначенный магазин и новую дату | Пять последних собственных записей | Нет | Нет | Нет |
| Руководитель | Не входит в базовый модуль | Не входит в базовый модуль | Не входит в базовый модуль | Нет | Не входит в базовый модуль |
| Администратор | Да, с выбором магазина | Все назначенные магазины за выбранную дату | Да, с обязательной причиной и новой версией | Да, с обязательной причиной и неизменяемой историей | Да, за выбранную дату |

## 2. Одна ежедневная запись

Все денежные значения хранятся в `RUB` с точностью до двух знаков, передаются с точкой и показываются с ровно одним пробелом перед `₽`. Поля не принимают отрицательные значения. Незаполненная расходная строка равна `0` и комментария не требует.

| Технический ключ | Видимое название | Смысл | Комментарий |
| --- | --- | --- | --- |
| `cash` | Нал | Наличные, передаваемые за день; размен, остающийся в кассе, сюда не включается | Не требуется |
| `cashless` | Б/Нал | Безналичные оплаты за операционную дату | Не требуется |
| `cash_expenses` | Расходы нал | Прочие наличные расходы, не подходящие к специальным строкам | Обязателен, если сумма больше `0` |
| `household_cash` | Хоз. нужды нал | Хозяйственные нужды наличными | Обязателен, если сумма больше `0` |
| `cleaning_cash` | Уборка нал | Уборка наличными | Обязателен, если сумма больше `0` |
| `salary_cash` | Зарплата нал | Зарплата наличными | Не требуется |
| `service_cash` | Выслуга нал | Выслуга наличными; название сохраняется в интерфейсе ровно в этой форме | Обязателен, если сумма больше `0` |
| `extra_payment_cash` | Доплата нал | Доплата наличными | Обязателен, если сумма больше `0` |
| `bonus_cash` | Премия нал | Премия наличными | Не требуется |
| `vacation_cash` | Отпускные нал | Отпускные наличными | Не требуется |
| `utilities_cash` | Коммунальные платежи нал | Коммунальные платежи наличными | Не требуется |
| `delivery_cash` | Доставка нал | Доставка наличными | Обязателен, если сумма больше `0` |

`Итого = Нал + Б/Нал + Расходы нал + Хоз. нужды нал + Уборка нал + Зарплата нал + Выслуга нал + Доплата нал + Премия нал + Отпускные нал + Коммунальные платежи нал + Доставка нал`.

Поле «Куда / зачем / за что» принадлежит именно строке расхода. Поэтому, например, «Уборка нал» и «Доставка нал» не смешиваются в одном общем комментарии. Для зарплаты, премии, отпускных и коммунальных платежей это поле не показывается и не сохраняется. Комментарий без ненулевой суммы не сохраняется.

## 3. Жизненный цикл и общий журнал

Продавец заполняет форму, видит живой расчет «Итого» и отправляет запись. После успешного создания она становится исторической: продавец не может изменить ее даже в тот же день. При обнаруженной ошибке он создает обращение администратору с пояснением; запись не редактируется обходным путем.

| Действие | Исполнитель | Поведение | Запись в существующем общем журнале |
| --- | --- | --- | --- |
| Создание | Продавец или администратор | Проверка прав, магазина, даты, неотрицательных сумм, уникальности и нужных пояснений | Исполнитель, магазин, дата, поля `до → после`, итог, строковые комментарии и время |
| Отклонение дубля | Система | Вторая активная запись за магазин и дату не сохраняется | Техническое событие без дублирования финансовой записи |
| Изменение | Только администратор | Создает следующую версию, сохраняет прежнюю и требует причину | Исполнитель, причина, версия, измененные поля `до → после`, магазин и время |
| Удаление из рабочего реестра | Только администратор | Помечает запись удаленной, увеличивает версию и требует причину; данные не уничтожаются | Исполнитель, причина, версия, `до → после`, магазин и время |
| Повторная передача после удаления | Продавец или администратор | Возвращает ту же запись как новую активную версию; первоначальные версии не изменяются | Исполнитель, новая версия, поля `до → после`, магазин и время |
| Печать | Только администратор | Печатает выбранную дату и выбранный магазин либо все магазины за эту дату | Дата, фильтр магазина, число магазинов и время |

Используется только существующий общий журнал и существующая функция `recordChange`; отдельный журнал для выручки не создается. Поиск общего журнала находит запись по магазину, пользователю, операционной дате и ID реестра. Доступ к содержимому ограничен серверной ролью: продавец не получает записи других магазинов через интерфейс, API или результаты поиска.

## 4. Экраны и печать

Страница продавца содержит короткую форму новой записи и ниже список пяти последних переданных записей. В карточке истории показываются дата, `Нал`, `Б/Нал`, сумма расходов и `Итого`.

Административная страница содержит только общий календарь **одной даты** и выбор магазина. В таблице выводится одна строка на магазин за выбранную дату с суммами, итогом и версией; «Изменить» и «Удалить» — компактные кнопки с иконками слева. Таблицу можно листать колесом, свайпом или перетаскиванием по горизонтали. Итоговая строка показывается в конце таблицы, потому что срез ограничен одной датой. Детализация раскрывает расходы и их комментарии.

Печать использует эту же компактную таблицу со строками-зебрами и итоговой строкой; после таблицы выводится список фактически сохраненных комментариев к расходам. Печать не меняет финансовую таблицу и не отправляет документ в Эвотор или 1С. Единые требования к будущим PDF/XLSX/CSV-выгрузкам, журналированию и ролям закреплены в [`reporting_and_export_expansion_spec.md`](./reporting_and_export_expansion_spec.md).

Новая страница наследует существующий светлый и темный стиль: без коралла в светлой теме и без iOS-синего в темной, с тематичными Select, одним заметным focus-контуром и hover без изменения геометрии. На телефоне поля показываются одной колонкой, а основные действия растягиваются на ширину. Перед каждым следующим расширением обязательна приемка светлой и темной тем на телефоне, средней и широкой ширине.

## 5. Граница с кассой и финансовым контуром

Реестр не пишет в Эвотор, 1С или старый Excel-импорт. В будущем он может показывать отдельный статус сверки с read-only кассовыми продажами Эвотор, но только после согласования состава чеков и правил размена. До этого значение `Итого` — введенный и журналируемый операционный факт магазина, а не автоматически признанная кассовая выручка и не финансовый факт существующего контура.

### 5.1 Приоритет для наличных расходных статей

Для строк `Расходы нал`, `Хоз. нужды нал`, `Уборка нал`, `Зарплата нал`, `Выслуга нал`, `Доплата нал`, `Премия нал`, `Отпускные нал`, `Коммунальные платежи нал` и `Доставка нал` источник выбирается отдельно для каждой связки «операционный магазин + бизнес-дата + статья». Система не назначает переходную дату и не предполагает, что новый период начинается одновременно у всех магазинов: источник определяется только наличием фактически сохраненной **активной** записи сайта.

| Активная запись «Выручки» на сайте | Значение в импортируемом Excel | Поведение импорта |
| --- | --- | --- |
| Есть | Любое, включая пустую ячейку | Ничего не менять в соответствующей расходной статье: сохраненная версия сайта имеет приоритет и не заменяется импортом |
| Нет | Передана сумма | Импортировать сумму по действующим правилам старого финансового Excel-контура |
| Нет | Ячейка пуста | Не создавать нулевой факт и не считать отсутствие значения нулем |

Повторный импорт не удаляет и не обнуляет ранее импортированное значение только потому, что в новой книге ячейка пуста, если активной записи «Выручки» за ту же статью, магазин и дату нет. Такое значение остается без изменения; система может показать статус «в новой книге значение не передано». Сайт и Excel не суммируются и не перезаписывают друг друга молча. Если для одной связки одновременно существуют заполненное значение Excel и активная запись «Выручки», то запись сайта сохраняет приоритет, а совпадение фиксируется как диагностический конфликт для разрешенной роли без изменения фактов.
