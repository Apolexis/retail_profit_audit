# Спецификация операционного реестра «Выручка» магазинов

**Статус:** согласованный проект для будущей реализации. Реестр собирает ежедневную операционную передачу выручки магазина и **не изменяет** финансовые факты, старый финансовый Excel-импорт, финансовые права, сессии или расчет прибыли. Это не кассовая команда Эвотор и не синхронизация с кассой.

> Смысл записи: наличные, которые сдаются за день, плюс безналичные оплаты и все наличные расходы за день дают операционную сумму, которую магазин фактически наторговал. Эта сумма может не совпасть с кассовой суммой из-за оставленного размена, времени закрытия дня, возвратов и других причин. Расхождение не исправляется автоматически.

## 1. Область доступа и неизменяемость

Одна запись относится к одному операционному магазину и одной бизнес-дате `Europe/Moscow`. Для пары «магазин + дата» допускается одна активная запись: повторная попытка продавца сообщает, что запись уже передана, и не создает дубль. Продавец видит только пять последних **собственных** записей по своей точке и вправе только создать новую; просмотр, изменение и удаление чужих записей сервером запрещены.

Администратор видит реестр всех магазинов, отбирает дату или период, создает запись с явным выбором магазина, редактирует существующую запись и печатает результат по всем магазинам. Удаление и для администратора не предусмотрено: ошибку исправляет новая версия той же записи с обязательной причиной. Измененная версия не стирает исходные данные.

| Роль | Создать | Просмотреть | Изменить | Удалить | Печать |
| --- | --- | --- | --- | --- | --- |
| Продавец | Только за назначенный магазин и новую дату | Пять последних собственных записей | Нет | Нет | Только собственную запись, если это будет отдельно разрешено |
| Руководитель | Не входит в базовый модуль | Не входит в базовый модуль | Не входит в базовый модуль | Нет | Не входит в базовый модуль |
| Администратор | Да, с выбором магазина | Все магазины, дата и период | Да, с обязательной причиной и новой версией | Нет | Да, за дату или период по всем магазинам |

## 2. Одна ежедневная запись

Все денежные значения хранятся в `RUB` с точностью до двух знаков, передаются с точкой и показываются с ровно одним пробелом перед `₽`. Поля не принимают отрицательные значения. В форме они начинаются с `0`; незаполненная расходная строка равна `0` и комментария не требует.

| Технический ключ | Видимое название | Смысл | Комментарий |
| --- | --- | --- | --- |
| `cash` | Нал | Наличные, передаваемые за день; размен, остающийся в кассе, сюда не включается | Не обязателен |
| `cashless` | Б/Нал | Безналичные оплаты за операционную дату | Не обязателен |
| `cash_expenses` | Расходы нал | Прочие наличные расходы, не подходящие к специальным строкам | Обязателен, если сумма больше `0` |
| `household_cash` | Хоз. нужды нал | Хозяйственные нужды наличными | Обязателен, если сумма больше `0` |
| `cleaning_cash` | Уборка нал | Уборка наличными | Обязателен, если сумма больше `0` |
| `salary_cash` | Зарплата нал | Зарплата наличными | Обязателен, если сумма больше `0` |
| `service_cash` | Выслуга нал | Выслуга наличными; название сохраняется в интерфейсе ровно в этой форме | Обязателен, если сумма больше `0` |
| `extra_payment_cash` | Доплата нал | Доплата наличными | Обязателен, если сумма больше `0` |
| `bonus_cash` | Премия нал | Премия наличными | Обязателен, если сумма больше `0` |
| `vacation_cash` | Отпускные нал | Отпускные наличными | Обязателен, если сумма больше `0` |
| `utilities_cash` | Ком. плат. нал | Коммунальные платежи наличными | Обязателен, если сумма больше `0` |
| `delivery_cash` | Доставка нал | Доставка наличными | Обязателен, если сумма больше `0` |

`Итого = Нал + Б/Нал + Расходы нал + Хоз. нужды нал + Уборка нал + Зарплата нал + Выслуга нал + Доплата нал + Премия нал + Отпускные нал + Ком. плат. нал + Доставка нал`.

Расход имеет собственное текстовое поле «Куда / зачем / за что». Заполнить сумму больше `0` и оставить этот текст пустым нельзя. Комментарий принадлежит именно строке расхода, поэтому, например, «Уборка нал» и «Доставка нал» не смешиваются в одном общем комментарии. Сумма `0` очищает необязательный черновой комментарий этой строки перед созданием записи, чтобы в реестре не оставалось объяснений без расхода.

## 3. Жизненный цикл и общий журнал

Продавец заполняет форму, видит живой расчет «Итого» и отправляет запись после подтверждения. После успешного создания форма становится исторической: продавец не может изменить ее даже в тот же день. При обнаруженной ошибке он создает обращение администратору с пояснением; запись не редактируется обходным путем.

| Действие | Исполнитель | Поведение | Запись в существующем общем журнале |
| --- | --- | --- | --- |
| Создание | Продавец или администратор | Проверка прав, магазина, даты, неотрицательных сумм, уникальности и комментариев расходов | Исполнитель, магазин, дата, поля `до → после`, итог, строковые комментарии и время |
| Отклонение дубля | Система | Вторая активная запись за магазин и дату не сохраняется | Техническое событие без дублирования финансовой записи |
| Редактирование | Только администратор | Создает следующую версию, сохраняет прежнюю и требует причину исправления | Исполнитель, причина, версия, измененные поля `до → после`, магазин и время |
| Печать | Только администратор по базовому правилу | Формирует документ за выбранную дату или период без изменения записей | Дата/период, фильтры, число магазинов, версия шаблона и время |

Используется только существующий общий журнал и существующая функция `recordChange`; отдельный журнал для выручки не создается. Поиск общего журнала находит запись по магазину, пользователю, операционной дате и ID реестра. Доступ к содержимому ограничен серверной ролью: продавец не получает записи других магазинов через интерфейс, API или результаты поиска.

## 4. Экраны и печать

Страница продавца содержит короткую форму новой записи и ниже список пяти последних переданных записей. В карточке истории показываются дата, `Нал`, `Б/Нал`, сумма расходов, `Итого`, статус и ссылка «Подробнее» только для чтения. Полные комментарии расходов раскрываются по требованию, чтобы не перегружать мобильную ширину.

Административная страница содержит фильтр «Дата» или «Период», магазин, автора и статус. Таблица выводит одну строку на магазин/дату с суммами и итогом; детализация раскрывает все расходы и их комментарии. Печать за дату или период формирует раздельные блоки по магазинам с датой, автором, всеми полями, строковыми комментариями, итогом и отметкой версии/времени печати. Она не меняет финансовую таблицу и не отправляет документ в Эвотор или 1С. Единые требования к будущим PDF/XLSX/CSV‑выгрузкам, журналированию и ролям закреплены в [`reporting_and_export_expansion_spec.md`](./reporting_and_export_expansion_spec.md).

Новая страница наследует существующий светлый и темный стиль: без коралла в светлой теме и без iOS-синего в темной, с тематичными Select, одним заметным focus-контуром и hover без изменения геометрии. На телефоне поля показываются одной колонкой, «Итого» остается закрепленным итоговым блоком без перекрытия нижней PWA-навигации; на средней и широкой ширине суммы и комментарии остаются в границах контейнера. До реализации обязательна приемка светлой и темной тем на телефоне, средней и широкой ширине.

## 5. Граница с кассой и финансовым контуром

Реестр не пишет в Эвотор, 1С или старый Excel-импорт. В будущем он может показывать отдельный статус сверки с read-only кассовыми продажами Эвотор, но только после согласования периода, состава чеков и правил размена. До этого значение `Итого` — введенный и журналируемый операционный факт магазина, а не автоматически признанная кассовая выручка и не финансовый факт существующего контура.

### 5.1 Приоритет для наличных расходных статей

Для строк `Расходы нал`, `Хоз. нужды нал`, `Уборка нал`, `Зарплата нал`, `Выслуга нал`, `Доплата нал`, `Премия нал`, `Отпускные нал`, `Ком. плат. нал` и `Доставка нал` источник выбирается отдельно для каждой связки «операционный магазин + бизнес-дата + статья». Система не назначает переходную дату и не предполагает, что новый период начинается одновременно у всех магазинов: источник определяется только наличием фактически сохраненной записи сайта.

| Запись «Выручки» на сайте | Значение в импортируемом Excel | Поведение импорта |
| --- | --- | --- |
| Есть | Любое, включая пустую ячейку | Ничего не менять в соответствующей расходной статье: сохраненная версия сайта имеет приоритет и не заменяется импортом |
| Нет | Передана сумма | Импортировать сумму по действующим правилам старого финансового Excel-контура |
| Нет | Ячейка пуста | Не создавать нулевой факт и не считать отсутствие значения нулем |

Повторный импорт не удаляет и не обнуляет ранее импортированное значение только потому, что в новой книге ячейка пуста, если записи «Выручки» за ту же статью, магазин и дату нет. Такое значение остается без изменения; система может показать статус «в новой книге значение не передано». Сайт и Excel не суммируются и не перезаписывают друг друга молча. Если для одной связки одновременно существуют заполненное значение Excel и запись «Выручки», то запись сайта сохраняет приоритет, а совпадение фиксируется как диагностический конфликт для разрешенной роли без изменения фактов.

Руководитель, которому назначена соответствующая операционная точка, вправе исправить запись «Выручки» с обязательной причиной и созданием следующей версии; продавец остается без права изменения. Администратор сохраняет это право по всем точкам. Любое исправление проходит через существующий общий журнал `recordChange` со значениями `до → после`, исполнителем, московским временем и причиной.
