# ТЗ разработчику 1С: выгрузки БМ/СРС и накладных магазинов

**Статус:** согласованный проектный контракт. Он описывает только подготовку данных **из 1С в приложение**. Выгрузка не создает, не проводит и не исправляет документы в 1С. Обмен с бухгалтерией/ЭДО не входит в это ТЗ: УПД будет загружаться в приложение вручную отдельным файлом с preview.

> **Граница систем.** В 1С существуют склады БМ и СРС, корректно введенные закупки/себестоимость и накладные на магазины. Регулярных остатков магазинов в 1С нет. Остатки действующих магазинов ведутся внутри приложения после стартовой инвентаризации; для **нового** магазина владелец может отдельно подготовить стартовый срез из 1С.

## 1. Формат и общие правила

На первом этапе допустимы один JSON-пакет на тип сущности либо XLSX/CSV с отдельными листами/файлами. Каждый пакет должен иметь `schema_version`, `source_system="1c_bm_srs"`, уникальный `batch_id`, `generated_at` в UTC, `business_timezone="Europe/Moscow"`, `mode` (`snapshot` или `delta`) и массив/лист `records`. Повторный импорт одинакового `batch_id` не должен создавать дубли.

Все значения количества и цен передаются числами с точкой как десятичным разделителем. Даты бизнеса — `YYYY-MM-DD`, время — RFC 3339 UTC. Ключ каждой записи стабилен: переименование товара, склада или адреса не меняет `source_record_id`.

| Пакет | Когда выгружать | Что делает приложение |
| --- | --- | --- |
| `products` | Полный срез при запуске, далее при изменении | В первом цикле попадает в очередь разового ручного сопоставления с внутренним товаром сайта; после подтверждения передает ID товара сайта как устойчивую ссылку |
| `inventory_snapshots` | Полный срез БМ/СРС при каждой выгрузке | Показывает фактический учетный остаток основных складов |
| `purchase_costs` | При новой закупке или изменении себестоимости | Использует в фактической закупочной аналитике |
| `store_shipments` | При проведении, отмене или исправлении накладной на магазин | Создает/обновляет ожидаемое поступление магазина после явного маппинга адреса |
| `new_store_opening_snapshot` | Только один раз при создании нового магазина | Формирует стартовый срез магазина из подготовленной владельцем выгрузки 1С |

## 2. Номенклатура `products`

### 2.1 Разовый маппинг и ID сайта в 1С

Сначала администратор вручную сопоставляет **существующую внутреннюю карточку товара сайта** и номенклатуру/характеристику 1С. Ни название, ни артикул поставщика, ни похожий штрихкод сами по себе связь не создают. Для каждой пары сохраняются `app_product_id`, `source_record_id`, исполнитель, время, основание и статус `confirmed`; неоднозначные строки остаются в очереди разбора и не влияют на остатки, продажи или рекомендации.

После утверждения маппинга разработчик 1С добавляет в номенклатуру отдельный пользовательский реквизит/свойство **«ID товара сайта»**. В нем хранится неизменяемый `app_product_id` (UUID/строка), а не название. Это значение передается в каждой последующей выгрузке `products`; изменение названия, категории, фасовки, кассового кода или штрихкода не меняет ID сайта. Удалять или присваивать это поле другой карточке нельзя: новая карточка получает новый ID только через явно подтвержденный маппинг и общий журнал.

### 2.2 Поля карточки

| Поле | Обязательное | Правило |
| --- | --- | --- |
| `source_record_id` | Да | Неизменяемый GUID/UUID карточки 1С или характеристики; это главный ключ |
| `app_product_id` | Нет до разового маппинга, затем да | Значение пользовательского реквизита 1С «ID товара сайта»; стабильный UUID/строка внутренней карточки сайта |
| `sku` | Да | Код/артикул 1С, уникальный в источнике |
| `name` | Да | Полное отображаемое наименование |
| `unit_name` | Да | Исходная единица 1С; не преобразовывать по названию вручную |
| `unit_precision` | Да | Разрешенное число знаков после запятой для количества |
| `barcodes` | Да | Массив всех допустимых штрихкодов; пустой массив разрешен, если штрихкода нет. Ручные коды сайта не затираются, а сверяются и дедуплицируются |
| `vat_rate`, `vat_included` | Да после настройки | В текущем бизнес-правиле только `10` или `22`; НДС включен в цену. Если источник не передал ставку, сайт применяет 10% как значение новой карточки и помечает ее для сверки, а не угадывает ставку по названию |
| `is_marked`, `marking_category` | Да / при наличии | Признак и значение только из утвержденного справочника маркировки сайта; индивидуальные коды маркировки 1С не выгружает по этому ТЗ |
| `is_alcohol`, `alcohol_codes` | Да / при наличии | Признак и массив технических алкокодов. Несколько значений не создают дубли и не заменяют коды другого источника без сверки |
| `alcohol_by_volume`, `alcohol_product_kind_code`, `tare_volume_l` | При категории «Алкоголь» или «Маркированное пиво» | Крепость в процентах, код вида АП (ФСРАР) и объем тары в литрах. Значения передаются как числа/строка кода, без правовой интерпретации в 1С |
| `is_active` | Да | Не удалять исторические товары; передавать `false` для выведенных из работы |

Приложение получает каталог Эвотор самостоятельно в server-side read-only режиме. Связь `Эвотор → 1С` строится сначала по подтвержденной тройке `evotor_product_uuid → source_record_id → app_product_id`, затем — только как кандидат по уникальному коду/штрихкоду вместе с единицей и точностью. Совпадение только по названию запрещено.

Техническая единица Эвотор `дроб` хранится в исходном поле вместе с `measurePrecision`, но после подтвержденного маппинга показывается пользователю как `кг`. Это **визуальное обозначение**, не пересчет количества и не потеря исходной единицы/точности. Для иных исходных единиц преобразование не допускается без отдельного подтвержденного правила.

### 2.3 Контролируемые значения маркировки и алкогольных полей

Разрешенный справочник `marking_category` содержит только: `БАД`; `Морепродукты (Икра/Консервы)`; `Алкоголь`; `Маркированное пиво`; `Безалкогольное пиво`; `Соковая продукция и безалкогольные напитки`; `Бутилированная питьевая вода`; `Молоко и молочная продукция`. Пустое значение допустимо для немаркируемого товара; произвольную новую категорию импорт не создает.

Для «Маркированного пива» обязательны алкокод(ы), крепость `%`, код вида АП и объем тары `L`. Пользовательские ориентиры для пивной продукции — код `500` при крепости до `8.6%` включительно и `510` при крепости выше `8.6%`; перед рабочим запуском бухгалтерия/ответственный за ЕГАИС подтверждает применимость и список кодов. Для категории «Алкоголь» те же поля видимы и проверяются на заполнение, но сайт не присваивает и не расширяет юридический справочник кодов АП без такого подтверждения.

## 3. Остатки БМ и СРС `inventory_snapshots`

Пакет содержит **полный** срез одного склада БМ или СРС на момент `as_of`; пропуск строки не означает нулевой остаток. Для нулевого остатка передается строка с `quantity_on_hand=0`.

| Поле | Обязательное | Правило |
| --- | --- | --- |
| `snapshot_id` | Да | Уникальный идентификатор полного среза |
| `source_record_id` | Да | Стабильный ID строки среза |
| `location_source_id` | Да | Ссылка на БМ или СРС |
| `product_source_id` | Да | Ссылка на `products.source_record_id` |
| `business_date`, `as_of` | Да | Операционная дата и точный момент среза |
| `quantity_on_hand` | Да | Фактический остаток в `unit_name` товара |
| `quantity_reserved`, `quantity_available` | Нет | Передавать при наличии учета резервов |
| `batch_ref`, `expiry_date` | Нет | Передавать при наличии партионного учета в 1С |

Эти численные остатки доступны руководителям и администраторам. Продавец в заявке видит только цветовой маркер доступности БМ/СРС, без числа.

## 4. Закупочная себестоимость `purchase_costs`

1С остается источником закупочной себестоимости, включая корректно внесенные вручную данные. УПД не заменяет этот поток.

| Поле | Обязательное | Правило |
| --- | --- | --- |
| `source_record_id` | Да | Стабильный ID строки поступления/расчета |
| `product_source_id`, `location_source_id` | Да / Нет | Товар и, если есть, склад учета |
| `effective_at` | Да | Момент применимости цены |
| `cost_per_base_unit`, `currency` | Да | Цена за единицу, на старте `RUB` |
| `includes_vat`, `vat_rate` | Да / Нет | НДС передается отдельно |
| `document_id`, `batch_ref` | Да / Нет | Основание аудита и партия при наличии |

## 5. Накладная БМ/СРС → магазин `store_shipments`

В 1С не нужно создавать магазинский остаток. Накладная должна однозначно показать, **на какой существующий адрес/магазин едет товар**. Приложение сопоставляет получателя вручную один раз, затем использует закрепленную связь.

### 5.1 Заголовок накладной

| Поле | Обязательное | Правило |
| --- | --- | --- |
| `shipment_id` | Да | Стабильный ID накладной 1С |
| `revision_id` | Да | Версия конкретной выгрузки накладной |
| `replaces_revision_id` | Нет | Ссылка на прежнюю версию при исправлении |
| `status` | Да | `posted`, `cancelled` или `corrected` |
| `document_number`, `issued_at`, `business_date` | Да | Видимый номер, время и дата |
| `origin_location_source_id` | Да | Только БМ или СРС |
| `destination_store_reference` | Да | Стабильный код/ID получателя, если он есть в 1С |
| `destination_address` | Да | Адрес из накладной для явного маппинга в приложение |

### 5.2 Строки накладной

| Поле | Обязательное | Правило |
| --- | --- | --- |
| `line_id`, `shipment_id` | Да | Стабильный ID строки и связь с заголовком |
| `product_source_id` | Да | Товар 1С |
| `quantity`, `unit_name` | Да | Отгруженное количество и его единица |
| `batch_ref`, `expiry_date` | Нет | Партия/срок при наличии |
| `retail_price_for_destination` | Нет | Розничная цена для данного магазина из вида цен 1С; используется для проверки цены, но не как закупочная себестоимость |
| `price_type_name` | Нет | Название вида цен 1С для объяснения происхождения розничной цены |

Повторная выгрузка руководителя с новым `revision_id` заменяет только **еще не подтвержденное** ожидаемое поступление. После приемки магазина исправление должно прийти как `corrected` с новой ревизией и разницей строк, чтобы история не переписывалась.

## 6. Стартовый срез только нового магазина `new_store_opening_snapshot`

Пакет не нужен для действующих магазинов: они начинают учет с закрытой стартовой инвентаризации. Для нового магазина владелец подготавливает из 1С один отдельный полный срез.

| Поле | Обязательное | Правило |
| --- | --- | --- |
| `opening_snapshot_id` | Да | Уникальный ID стартового среза |
| `destination_store_reference`, `destination_address` | Да | Получатель, заранее сопоставленный с новым магазином приложения |
| `business_date`, `as_of` | Да | Дата и момент начала учета |
| `product_source_id`, `quantity`, `unit_name` | Да | Полный товарный состав и количество |
| `prepared_by` | Да | Кто подготовил срез в 1С |

Импорт происходит через preview и явное подтверждение администратора. Повторное применение одного `opening_snapshot_id` запрещено.

## 7. Что не требуется от разработчика 1С

Разработчик не передает регулярные остатки магазинов, кассовые чеки, клиентов, бонусы, УПД, индивидуальные коды маркировки, пароли, токены или данные карт лояльности. УПД загружается вручную администратором отдельным файлом; коды маркировки, если они есть в этом файле, хранятся только на сервере. Конкретная марка не используется для определения маршрута накладной: она может быть установлена только по сканированию в кассовом чеке и показывает место продажи. Ручные штрихкоды/алкокоды в сайте не требуют обратной записи в 1С на первом этапе.

## 8. Первый тестовый пакет

Для приемки разработчик передает один полный срез БМ или СРС, 10–20 товаров с разными единицами/точностью, 2–3 закупочные цены и одну реальную накладную на существующий магазин с адресом, строками и розничной ценой из вида цен 1С. Все пакеты сначала обрабатываются в preview: они не меняют 1С, кассу, финансовые данные или рабочие остатки.

## 9. Результат работы разработчика

Разработчик передает описание формата, тестовый пакет и инструкцию повторной выгрузки. Только после проверки preview будет согласовано: оставить файловый импорт либо перейти к защищенному read-only API. Обратный обмен в 1С не входит в текущую задачу.
