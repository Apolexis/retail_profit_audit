# Спецификация обмена для товарного учета: 1С, Эвотор и «Аналитика „Рыбный“»

**Статус:** проектный контракт для разработчика 1С. **Не является разрешением на синхронизацию или запись данных.** На дату документа система не создает кассовые чеки, остатки, перемещения, заявки или изменения в 1С/Эвотор. Финансовые факты, их Excel-импорт, права и сессии остаются изолированными от будущего товарного контура. Отдельное ТЗ для бухгалтерии/ЭДО по УПД и кодам маркировки находится в [`accounting_upd_export_task.md`](./accounting_upd_export_task.md).

Практическая очередность запуска и краткое ТЗ для разработчика 1С приведены в [`practical_operational_accounting_plan.md`](./practical_operational_accounting_plan.md).

> Уточнение владельца: в 1С существуют только склады БМ и СРС, а также накладные от этих складов на магазины. Магазинов и их остатков в 1С нет. Фактический остаток магазина будет вестись в «Аналитике „Рыбный“» как собственный регистр движений.

> Цель первого этапа — получить воспроизводимые, проверяемые и идемпотентные данные об остатках, продажах и закупочной себестоимости. Любые обратные действия в 1С, Эвоторе или кассах допускаются только после отдельного письменного согласования.

## 1. Целевая роль систем

| Система | Роль | Разрешенное направление на первых этапах | Не допускается без отдельного решения |
| --- | --- | --- | --- |
| **1С** | Исходный контур складов БМ/СРС, номенклатуры, корректно введенных закупок/себестоимости и накладных отправки в магазины | Выгрузка складских справочников, остатков БМ/СРС, себестоимости и накладных | Создание или проведение документов, корректировка остатков, цен и себестоимости |
| **Бухгалтерия / ЭДО** | Документное подтверждение приемки через подписанные УПД, детализация партий, сроков и маркировки | Read-only выгрузка документов/строк для сверки с 1С и регистрации маркированных единиц | Замена закупочной себестоимости 1С, проведение УПД или изменение статусов в ЭДО |
| **Эвотор Облако V2** | Источник факта розничных продаж, чеков и кассовой номенклатуры | Только серверное read-only получение данных после утверждения перечня методов | Кассовые операции, изменение товаров, цен, скидок, чеков, остатков или настроек |
| **«Аналитика „Рыбный“»** | Собственный регистр фактических остатков магазинов, нормализация, сопоставление, сверка, рекомендации и заявки | Начальные инвентаризации, накладные из 1С, продажи Эвотор, внутренние перемещения, списания, возвраты и инвентаризации | Автоприменение перемещений, заказов или закупок в 1С/Эвоторе |

Справочник `stores` текущего финансового контура не должен переиспользоваться как первичный идентификатор обмена. Для будущего учета создается отдельное сопоставление локаций с явным `location_code`; магазины создаются в приложении и не предполагаются существующими в 1С. Связь с торговой точкой допускается только после ручной проверки администратором.

### 1.1 Источник истины для остатков

| Контур | Что считается источником истины | Как появляется остаток |
| --- | --- | --- |
| БМ и СРС | 1С | Полный складской snapshot и, при наличии, движения из 1С |
| Магазин | «Аналитика „Рыбный“» | Начальная инвентаризация + накладные 1С на магазин − продажи Эвотор − списания ± возвраты/корректировки ± подтвержденные перемещения |

Для магазина нельзя подменять остаток данными 1С или пытаться получить его из Эвотора: до первой начальной инвентаризации остаток имеет статус `unknown` и не участвует в рекомендациях. Каждая последующая инвентаризация формирует отдельное корректирующее событие, а не перезаписывает историю.

### 1.2 Минимальная выгрузка 1С

| Пакет | Содержимое | Обязательное условие |
| --- | --- | --- |
| `locations` | Только БМ и СРС | Стабильные `source_record_id` и коды `BM`/`SRS` |
| `products` | Номенклатура, единица, штрихкоды, маркировка, алкоголь | Ключ — стабильный ID 1С, не наименование |
| `inventory_snapshots` | Остатки только БМ и СРС | Полный срез каждого склада на момент `as_of` |
| `purchase_costs` | Историческая закупочная себестоимость | Цена за базовую единицу, НДС, документ-основание |
| `store_shipments` и `store_shipment_lines` | Накладные из БМ/СРС на магазин | Должны содержать стабильный ID накладной, склад-отправитель и `destination_store_reference` — код/идентификатор получающего магазина, по которому приложение выполнит явный маппинг |

## 2. Общий транспортный контракт

Рекомендуемый основной вариант — пакетный **HTTPS JSON API** с аутентификацией сервисной учетной записью 1С. Пока API не готов, допустим CSV/XLSX-файл той же структуры. Один пакет содержит только один тип сущности. Данные передаются в UTF-8, числовые значения — JSON numbers или строки с точкой как десятичным разделителем, без пробелов-разделителей тысяч.

| Поле конверта | Тип | Обязательное | Правило |
| --- | --- | --- | --- |
| `schema_version` | string | Да | Начать с `1.0`; несовместимое изменение требует новой major-версии |
| `source_system` | string | Да | Например, `1c_bm_srs` или `evotor_cloud_v2` |
| `entity` | string | Да | Один из контрактных типов из раздела 3 |
| `batch_id` | UUID/string | Да | Уникален в пределах `source_system`; повтор того же `batch_id` не должен создавать дубликаты |
| `mode` | enum | Да | `snapshot` для полного среза либо `delta` для новых/измененных событий |
| `generated_at` | RFC 3339 UTC | Да | Момент формирования пакета источником |
| `business_timezone` | IANA string | Да | На старте строго `Europe/Moscow` |
| `as_of` | RFC 3339 UTC | Да для snapshot | Состояние данных на этот момент |
| `records` | array | Да | Массив объектов одного типа |
| `checksum_sha256` | string | Рекомендуется | SHA-256 от канонического тела пакета без этого поля |

Идемпотентный ключ каждой записи: `source_system + entity + source_record_id`. Для событий дополнительно обязателен `event_id`; изменение уже принятого события передается новым `event_id` со ссылкой `reverses_event_id`, а не незаметной перезаписью истории.

## 3. Сущности и обязательные поля

### 3.1 Локации `locations`

Одна локация — магазин, склад БМ, склад СРС, транзитная зона либо списание. Коды `BM` и `SRS` закрепляются как складские локации, если именно так они ведутся в 1С.

| Поле | Тип | Обязательное | Комментарий |
| --- | --- | --- | --- |
| `source_record_id` | string | Да | Неизменяемый UUID/GUID 1С либо иной стабильный ключ |
| `location_code` | string | Да | Короткий уникальный бизнес-код: `BM`, `SRS`, `STORE_N95` |
| `name` | string | Да | Отображаемое имя |
| `location_type` | enum | Да | `warehouse`, `store`, `transit`, `writeoff` |
| `is_active` | boolean | Да | Локация не удаляется из истории |
| `address` | string/null | Нет | Адрес магазина/склада |
| `financial_store_reference` | string/null | Нет | Только явная ссылка для последующего ручного маппинга |

### 3.2 Номенклатура `products`

Карточка товара не зависит от названия у поставщика. Нельзя использовать наименование как ключ. Несколько штрихкодов передаются массивом; одна карточка может иметь несколько вариантов фасовки только при разных стабильных `source_record_id` или отдельной сущности варианта.

| Поле | Тип | Обязательное | Комментарий |
| --- | --- | --- | --- |
| `source_record_id` | string | Да | Стабильный ID 1С номенклатуры/характеристики |
| `sku` | string | Да | Внутренний артикул/код 1С; уникален в источнике |
| `name` | string | Да | Полное торговое наименование |
| `base_unit` | enum | Да | `piece`, `kg`, `g`, `l`, `ml`; для потребительской упаковки — фактическая базовая единица учета |
| `unit_precision` | integer | Да | Допустимое число знаков количества, обычно `0` для шт. и до `3` для веса |
| `barcodes` | array[string] | Да | EAN/GTIN/внутренние коды, без пробелов и повторов |
| `is_active` | boolean | Да | Не удалять устаревший товар из истории |
| `brand` | string/null | Нет | Бренд/производитель, если он ведется в 1С |
| `category_path` | array[string] | Нет | Иерархия категории; не подменяет отдельный справочник категорий приложения |
| `vat_rate` | number/null | Нет | Ставка НДС как число, например `20` |
| `is_marked` | boolean | Да | Признак обязательной маркировки |
| `marking_type` | string/null | Да при `is_marked=true` | Тип маркировки источника |
| `is_alcohol` | boolean | Да | Признак алкогольной номенклатуры |
| `alcohol_code` | string/null | Да при `is_alcohol=true` | Идентификатор, используемый в 1С/ЕГАИС, без попытки преобразовать его |

### 3.3 Снимки остатков `inventory_snapshots`

Полный срез из 1С обязателен минимум раз в сутки **только по БМ и СРС**. Один `snapshot_id` должен содержать полный набор строк по указанному складу; неполный срез отклоняется либо получает статус `partial` и не участвует в складской сверке. Остатки магазинов не выгружаются из 1С: в приложении они строятся по собственному регистру движений и подтверждаются инвентаризацией.

| Поле | Тип | Обязательное | Комментарий |
| --- | --- | --- | --- |
| `snapshot_id` | string | Да | Уникальный ID среза в источнике |
| `source_record_id` | string | Да | ID строки снимка либо составной стабильный ключ |
| `location_source_id` | string | Да | Ссылка на `locations.source_record_id` |
| `product_source_id` | string | Да | Ссылка на `products.source_record_id` |
| `business_date` | `YYYY-MM-DD` | Да | Операционная дата по Москве |
| `as_of` | RFC 3339 UTC | Да | Точный момент остатка |
| `quantity_on_hand` | number | Да | Фактический учетный остаток; допускается отрицательное значение только при явном флаге источника |
| `quantity_reserved` | number/null | Нет | Резерв, если ведется |
| `quantity_available` | number/null | Нет | Доступно к продаже/перемещению |
| `batch_ref` | string/null | Нет | Партия/серия, если остатки ведутся партионно |
| `expiry_date` | `YYYY-MM-DD`/null | Нет | Срок годности партии |

### 3.4 Накладные 1С на магазины `store_shipments`, `store_shipment_lines`

Это единственный обязательный поток 1С, который влияет на остаток магазина. Накладная фиксирует отправку из БМ или СРС на магазин, но не предполагает наличия карточки магазина или остатка магазина в 1С. После явного сопоставления `destination_store_reference` приложение создает внутри своего регистра парные события: расход со склада-источника и приход в магазин. Повторная загрузка той же накладной не должна создать повторный приход.

| Поле | Тип | Обязательное | Комментарий |
| --- | --- | --- | --- |
| `shipment_id` | string | Да | Стабильный ID накладной 1С |
| `source_record_id` | string | Да | Уникальный ID заголовка или строки документа в 1С |
| `issued_at` | RFC 3339 UTC | Да | Время проведения накладной в 1С |
| `business_date` | `YYYY-MM-DD` | Да | Дата по `Europe/Moscow` |
| `origin_location_source_id` | string | Да | Только БМ или СРС |
| `destination_store_reference` | string | Да | Код/ID магазина в накладной; сопоставляется с магазином приложения вручную |
| `status` | enum | Да | `posted`, `cancelled`, `corrected`; отмена и корректировка передаются отдельным событием |
| `document_number` | string/null | Нет | Отображаемый номер накладной |
| `line_id` | string | Да, в строке | Стабильный ID строки накладной |
| `product_source_id` | string | Да, в строке | Ссылка на `products.source_record_id` |
| `quantity` | number | Да, в строке | Положительное количество в базовой единице |
| `batch_ref` | string/null | Нет | Партия, серия или срок годности |

### 3.5 Внутренний регистр магазинов `store_stock_ledger`

Этот регистр живет только в приложении. Каждая строка неизменяема и имеет `event_id`, время, магазин, товар, знаковое количество, источник и ссылку на первичный документ. Разрешены типы `opening_stocktake`, `shipment_in`, `sale`, `sale_return`, `writeoff`, `transfer_in`, `transfer_out`, `stocktake_adjustment`. Нельзя изменять прошлый остаток прямым редактированием: инвентаризация добавляет `stocktake_adjustment`, а отмена внешнего события создает новое событие со ссылкой `reverses_event_id`.

До первой начальной инвентаризации у магазина нет «нулевого» остатка — есть состояние `unknown`. Продажи из Эвотора не должны формировать отрицательный остаток бесконтрольно: при отсутствии начального остатка, неразобранной номенклатуре или недостатке товара запись попадает в очередь сверки и сигналов.

Для всех локаций прикладной контур дополнительно ведет распределение движения по партиям и срокам. Если продажа Эвотор не содержит точной партии, она списывается расчетно по FEFO (ближайший срок годности); если срок не известен — по FIFO с явной отметкой. Точный маркировочный/партионный идентификатор при наличии всегда имеет приоритет над расчетом. Детальный сценарий партий, сроков и ролевого доступа приведен в [`practical_operational_accounting_plan.md`](./practical_operational_accounting_plan.md).

### 3.6 Закупочная себестоимость `purchase_costs`

Потребуются именно исторические факты цены закупки из 1С, а не только текущая цена товара. Ручной ввод в 1С допустим и используется как факт, поскольку владелец подтвердил корректность этих данных. Валюта на первом этапе — `RUB`; НДС передается отдельным признаком, чтобы не смешивать суммы.

| Поле | Тип | Обязательное | Комментарий |
| --- | --- | --- | --- |
| `source_record_id` | string | Да | Уникальный ID строки поступления/расчета себестоимости |
| `product_source_id` | string | Да | Ссылка на товар |
| `location_source_id` | string/null | Нет | Склад поступления/учета |
| `effective_at` | RFC 3339 UTC | Да | Когда цена стала применимой |
| `cost_per_base_unit` | number | Да | Цена за базовую единицу, до округления интерфейсом |
| `currency` | string | Да | На старте `RUB` |
| `includes_vat` | boolean | Да | Включен ли НДС в цене |
| `vat_rate` | number/null | Нет | Ставка НДС |
| `supplier_source_id` | string/null | Нет | Справочник контрагента 1С, если разрешено передавать |
| `document_id` | string | Да | Поступление/корректировка, обеспечивающее аудит |
| `batch_ref` | string/null | Нет | Для партионной себестоимости |

### 3.7 УПД бухгалтерии/ЭДО `edi_upd`, `edi_upd_lines`, `edi_marking_units`

УПД не заменяет закупку/себестоимость из 1С, а дает документное основание для ее сверки и точную детализацию приемки. В соответствии с порядком ЭДО маркированной продукции покупатель сверяет УПД с фактическим поступлением и подписывает его при отсутствии расхождений; после этого оператор ЭДО передает сведения о смене собственника в систему маркировки.[2]

| Поле | Тип | Обязательное | Комментарий |
| --- | --- | --- | --- |
| `upd_id` | string | Да | Стабильный ID УПД в ЭДО/бухгалтерии |
| `document_number` | string | Да | Видимый номер УПД |
| `issued_at`, `accepted_at` | RFC 3339 UTC | Да | Дата документа и подтверждения приемки покупателем |
| `status` | enum | Да | `draft`, `signed_by_seller`, `accepted`, `corrected`, `cancelled`; в складской факт попадает только `accepted` |
| `supplier_reference` | string | Да | Стабильная ссылка на поставщика/контрагента, если разрешено передавать |
| `receipt_location_code` | string | Да | БМ/СРС либо иной код локации, сопоставленный вручную перед применением |
| `source_purchase_document_id` | string/null | Нет | Ссылка на документ/строку 1С для сверки, не для подмены себестоимости |
| `line_id`, `product_source_id` | string | Да, в строке | Стабильный ID строки и товар 1С после явного сопоставления |
| `quantity`, `unit_price`, `line_total`, `vat_rate` | number | Да, в строке | Количество, цена и НДС для проверки с 1С |
| `batch_ref`, `manufactured_at`, `expiry_date` | string/date/null | Нет | Партия и сроки, если они есть в УПД или связанной приемке |
| `marking_unit_id` | protected string/null | Нет | Индивидуальный код маркировки только в защищенном серверном контуре; не выводится в журнал/обычный UI |
| `marking_status` | enum/null | Нет | Технический статус единицы, достаточный для контроля жизненного цикла |

Перед применением УПД приложение проверяет его статус, локацию, товар, количество и ссылку на документ 1С. Расхождение создает сигнал и очередь сверки; оно не переписывает себестоимость 1С и не удаляет принятый документ. Для маркированной единицы `marking_unit_id` создается связь с партией и локацией, а последующие накладная, продажа, возврат и списание меняют ее статус только в пределах подтвержденных событий.

### 3.8 Продажи и чеки `sales_receipts`, `sales_receipt_lines`

Этот поток формируется из Эвотор только после отдельного утверждения набора read-only методов. Чек без строк считается ошибкой пакета. Персональные данные покупателя, полные номера карт лояльности и платежные токены в первом контракте **не передаются**.

| Поле | Тип | Обязательное | Комментарий |
| --- | --- | --- | --- |
| `receipt_id` | string | Да | Стабильный ID чека источника |
| `receipt_number` | string/null | Нет | Отображаемый номер для поиска |
| `location_source_id` | string | Да | Касса/магазин должен быть сопоставлен с `locations` |
| `closed_at` | RFC 3339 UTC | Да | Время закрытия чека |
| `business_date` | `YYYY-MM-DD` | Да | Дата по Москве |
| `status` | enum | Да | `closed`, `returned`, `cancelled` |
| `gross_total` | number | Да | Итог чека с учетом скидок |
| `discount_total` | number | Да | Сумма скидок, `0` при отсутствии |
| `payment_summary` | array | Нет | Только агрегированные типы и суммы оплаты |
| `line_id` | string | Да, в строке | Уникальный ID строки чека |
| `product_source_id` | string/null | Да | Маппинг на мастер товара; `null` допускается лишь в quarantine до ручного сопоставления |
| `source_item_id` | string | Да | Кассовый ID позиции для последующего маппинга |
| `quantity` | number | Да | Положительное количество для продажи; возврат отражается статусом/отдельной строкой по правилам источника |
| `unit_price` | number | Да | Цена за единицу до скидки |
| `line_discount` | number | Да | `0` при отсутствии |
| `line_total` | number | Да | Итог строки после скидки |
| `barcode` | string/null | Нет | Сканированный/карточный код, если источник его дает |
| `marking_code_status` | string/null | Нет | Только технический статус без раскрытия чувствительных кодов |

Официальная документация Эвотор должна оставаться первоисточником для разрешенных методов, версий заголовков, ограничений и полей облачного API; перед реализацией разработчик подтверждает их по актуальному разделу API Облака V2.[1]

### 3.9 Заявки на перемещение и группы печати

Заявка в приложении на раннем этапе — только предложение/документ ожидания. Ее печатная разбивка строится правилом, а не хардкодом в интерфейсе.

| Сущность | Ключевые поля | Правило |
| --- | --- | --- |
| `transfer_requests` | `request_id`, `from_location_source_id`, `to_location_source_id`, `requested_by`, `requested_at`, `needed_by`, `status`, `comment` | Статусы: `draft`, `submitted`, `approved`, `rejected`, `fulfilled`, `cancelled`; до интеграции с 1С `approved` не создает движение |
| `transfer_request_lines` | `line_id`, `request_id`, `product_source_id`, `requested_qty`, `approved_qty`, `reason`, `priority` | Количество в базовой единице; `approved_qty` не превышает `requested_qty` без отдельного основания |
| `print_groups` | `print_group_code`, `name`, `is_active` | Например, `BM_FROZEN`, `SRS_FRESH`; состав групп редактируется администратором |
| `print_group_rules` | `print_group_code`, `from_location_source_id`, `product_category_ref`, `product_source_id`, `priority` | Приоритет: конкретный товар → категория → склад по умолчанию; результат должен быть объясним в preview печати |

## 4. Сопоставления, контроль качества и сверка

### Обязательные маппинги

| Маппинг | Ключ | Правило разрешения конфликта |
| --- | --- | --- |
| 1С-локация → локация приложения | `location_source_id` | Автоматическое совпадение только для БМ и СРС по закрепленному `location_code`; остальные — в очередь ручного подтверждения |
| Накладная 1С → магазин приложения | `destination_store_reference` | Только явный администраторский маппинг; до него накладная не влияет на остатки магазина |
| Эвотор-касса/магазин → локация | `evotor_store_id`/кассовый ID | Только явное администраторское сопоставление |
| Позиция Эвотор → товар 1С | `source_item_id`, штрихкод, единица | Сначала стабильный ID, затем уникальный штрихкод и единица; неоднозначность не объединять автоматически |
| Поставщик из прайс-контроля → контрагент 1С | отдельная таблица соответствий | Нужна лишь для сравнения прайса с фактической себестоимостью; никогда не связывать по названию без подтверждения |

### Правила приемки и quarantine

1. Пакет отклоняется, если нет `batch_id`, версии схемы, времени формирования или ссылочного ключа.
2. Запись с неизвестной локацией или товаром принимается только в изолированную очередь `quarantine`; она не влияет на остатки, рекомендации и финансовые графики.
3. Снимок 1С должен быть полным на уровне БМ или СРС. Нулевой остаток передается явной строкой, а не удалением строки.
4. Остаток магазина меняется только внутренними событиями регистра; исходный `event_id` остается доступен для аудита, а отмена передается отдельным событием.
5. Количества и деньги не округляются при импорте. Округление выполняется только при отображении; валютные суммы хранятся как decimal с точностью не менее 4 знаков для unit cost и 2 знаков для итогов.

### Ежедневная сверка

После начальной инвентаризации магазина и появления накладных/продаж приложение рассчитывает, но не корректирует автоматически:

`ожидаемый остаток = вчерашний подтвержденный остаток + поступления + transfer_in − transfer_out − продажи − списания ± корректировки`.

Результат сверяется с очередной подтвержденной магазинской инвентаризацией. Расхождение фиксируется как сигнал с указанием товара, магазина, периода, абсолютной и относительной разницы. Сигнал не меняет факты и не создает документ в 1С/Эвоторе.

## 5. Порядок реализации и контрольные точки

| Этап | Результат | Направление | Условие перехода |
| --- | --- | --- | --- |
| **0. Справочники и маппинг** | Утверждены БМ/СРС, магазины приложения, товары, единицы, штрихкоды и таблица соответствий | 1С → preview | Не менее 95% активных складских строк имеет стабильные ключи; неоднозначности вынесены отдельно |
| **1. Склады 1С** | Preview `locations`, `products`, `inventory_snapshots`, `purchase_costs` только БМ/СРС | Только чтение | Полные срезы БМ и СРС проходят валидацию без записи в рабочие остатки |
| **2. Накладные 1С** | `store_shipments` из БМ/СРС на магазины | Только чтение | Повтор накладной не создает дубль; получатель вручную сопоставлен с магазином приложения |
| **3. Начальные остатки магазинов** | Подтвержденная начальная инвентаризация в приложении | Внутри приложения | Для магазина сформирован начальный регистр остатков, а не искусственный ноль |
| **4. Эвотор discovery** | Подтверждены доступные магазины, кассы и read-only сущности | Только чтение | Согласован перечень методов и маппинг Эвотор → магазины; секрет не показывается в UI/логах |
| **5. Продажи и сверка** | Read-only чеки/строки, внутренний регистр, инвентаризации, покрытие и рекомендации | Только чтение + внутренний регистр | Расхождения продаж, накладных и инвентаризаций объяснимы в отчете исключений |
| **6. Заявки и печать** | Заявки продавцов, preview разбивки печати по БМ/СРС | Внутри приложения | Утверждение создает только внутренний статус; выгрузка/создание документа 1С — отдельный этап |
| **7. Двусторонний обмен** | Возможная передача заявок/перемещений в 1С | Запись, только после отдельного решения | Отдельный аудит прав, обработка ошибок, подтверждение оператором и аварийный rollback-план |

## 7. Решения, которые нужны от владельца и разработчика 1С до начала обмена

| Вопрос | Требуемое решение |
| --- | --- |
| Стабильные ключи | Подтвердить, какие GUID 1С доступны и не меняются при переименовании карточки/склада |
| Единицы | Утвердить базовую единицу для весового товара и допустимую точность количества |
| Складская логика | Подтвердить, что 1С передает только БМ и СРС; магазины создаются и ведутся внутри приложения |
| Накладные на магазин | Утвердить стабильный ID накладной, строк и получателя `destination_store_reference`; он должен однозначно определить магазин в приложении |
| Начальная инвентаризация | Определить дату старта, ответственного и правила ввода начального фактического остатка каждого магазина |
| Магазинские корректировки | Утвердить причины и роли для списаний, возвратов, пересчета и внутренних перемещений; прошлые события не редактируются |
| Себестоимость | Определить метод (последняя закупка, средняя, FIFO, партия) и момент ее признания |
| Продажи Эвотор | Согласовать, какие типы чеков, возвраты и оплаты входят в факт продаж |
| Маркировка/алкоголь | Утвердить, какие технические поля действительно можно передавать, не копируя секретные коды и персональные данные |
| Расписание | Не вводить фоновый обмен, пока не будут утверждены частота, окно сверки и обработка повторов/ошибок |
| УПД и маркировка | Бухгалтерия подтверждает источник выгрузки УПД, связь с документами 1С, наличие партий/сроков и возможность безопасно передавать коды маркировки |
