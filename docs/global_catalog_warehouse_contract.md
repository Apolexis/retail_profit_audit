# Контракт общего справочника, видов цен и складов

**Статус:** утвержденная техническая последовательность для следующей миграции операционного контура. Документ не включает обмен с 1С или Эвотором и не меняет финансовый контур.

> **Принцип:** товар является общим объектом сети; магазин является складом (операционной точкой) и получает назначенный вид продажной цены. Кассовая запись Эвотор — только read-only внешний идентификатор товара на конкретной точке, а не отдельный товар сети.

## Граница и инварианты

| Инвариант | Решение |
| --- | --- |
| Финансовые факты и Excel | Не читаются, не пересчитываются и не меняются в этой миграции. |
| Каталог ПОРТ | Все 816 подтвержденных позиций сохраняют существующие первичные ключи, точные наименования, коды, НДС, штрихкоды и внутреннюю себестоимость. Автоматическое объединение или дублирование не выполняется. |
| Эвотор | Только серверное чтение Cloud API V2. В схеме предусмотрен флаг разрешения выгрузки, но нет процедуры, кнопки действия или outbound-запроса в Эвотор. |
| Аудит | Любое будущее создание, изменение, скрытие, назначение вида цен или ручная связь кассового ID проходит через существующий `recordChange`. Техническая schema/data-миграция не редактирует бизнес-факты. |
| История инвентаризаций | Существующие `productId` в строках и движениях остаются прежними. Они уже становятся идентификаторами общих товаров, поэтому история не требует перепривязки. |

## Целевая модель

### Общая номенклатура

Существующая таблица `operational_catalog_products` становится общим реестром продуктов. В переходной схеме ее поле `storeId` сохраняется как **источник первоначального read-only подтверждения**: оно больше не ограничивает видимость товара на другой точке и не означает владение товаром конкретным магазином. Сохранение поля исключает риск скрытого изменения идентификаторов уже подтвержденных позиций и исторических пересчетов.

К товару добавляются следующие атрибуты.

| Поле | Тип и правило |
| --- | --- |
| `markingCategory` | Закрытый enum: «Нет», «БАД», «Морепродукты · икра», «Морепродукты · консервы», «Алкоголь», «Маркированное пиво», «Безалкогольное пиво», «Соковая продукция и безалкогольные напитки», «Бутилированная питьевая вода», «Молоко и молочная продукция». По умолчанию «Нет». |
| `manualBarcodes` | Строка ручных штрихкодов, разделитель строго `;`. Пустая строка допустима. Кассовые штрихкоды `barcodes` остаются исходными read-only данными. |
| `isVisibleInRequests` | Булево значение, по умолчанию `true`. При `false` товар не показывается в будущих заявках; это не удаление и не влияет на историю. |
| `isEvotorExportEnabled` | Булево значение, по умолчанию `false`. Это только административный флаг будущего разрешения; во время этого этапа функциональная выгрузка отсутствует. |
| `internalCostPrice` | Уже существующая внутренняя себестоимость, редактируемая только администратором и никогда не отправляемая в Эвотор. |

### Виды цен и назначение магазина

| Таблица | Ключи | Назначение |
| --- | --- | --- |
| `operational_price_types` | `id`, уникальные `name` и `normalizedName`, `isDefault`, `isActive` | Редактируемые виды продажных цен сети. Первая системная запись: **«Розничная»**. |
| `operational_store_price_types` | уникальный `storeId`, `priceTypeId` | Одно назначение активного вида цены для магазина-склада. При миграции «Розничная» назначается всем существующим магазинам без изменения товаров. |
| `operational_product_sale_prices` | уникальная пара `productId + priceTypeId` | Продажная цена товара по виду цен. Отсутствие строки означает «цена не задана», а не ноль. |

### Привязки кассового каталога

Новая таблица `operational_evotor_product_links` содержит уникальную пару `storeId + evotorProductId` и ссылку `productId` на общий товар. Миграция заполнит ее из 816 сохраненных строк ПОРТ. В будущем кассовый идентификатор не будет автоматически объединяться с похожим наименованием: неизвестная кассовая позиция остается отдельной до явного подтверждения администратора. Это исключает неверное сопоставление разных продуктов и не нарушает read-only границу.

## Поведение экранов после миграции

| Экран | Поведение |
| --- | --- |
| **Номенклатура** | Показывает единый список сети, а не фильтрует товары по магазину. Карточка содержит НДС 10%/22%, закрытый список маркировки, ручные штрихкоды с `;`, внутреннюю себестоимость, видимость для заявок и флаг будущей выгрузки. Цена вводится отдельной строкой для выбранного вида цен. |
| **Склад** | Новый отдельный экран. Магазины отображаются как склады, у каждой точки виден назначенный вид цен. Отдельный read-only список Эвотор показывает только закрепленное соответствие, без адреса и без выбора чужой кассы. |
| **Остатки** | По каждой доступной точке показывает общие товары и ее учетное количество. До первой инвентаризации значение остается «Не посчитан». Цены и себестоимость не показываются продавцу или руководителю. |
| **Инвентаризации** | Выбирают общий активный товар; учетное количество всегда считается в контексте магазина-склада. Исторические строки сохраняют существующий `productId`. |

## Детальная миграционная последовательность

1. Создать таблицы видов цен, назначения магазина, продажных цен и read-only кассовых связей.
2. Добавить атрибуты общего товара к `operational_catalog_products` с безопасными default-значениями.
3. Создать единственную цену «Розничная», назначить ее всем существующим магазинам, если назначение еще отсутствует.
4. Скопировать существующие пары `storeId + evotorProductId → productId` в `operational_evotor_product_links`. Товары, цены, остатки и история в этом шаге не меняются.
5. Изменить выборки так, чтобы рабочий каталог был общим, а остатки и инвентаризации фильтровались по складу только на уровне движения/учетного количества.
6. Добавить административные tRPC-операции с `recordChange` для видов цен, назначения вида цены магазину, продажной цены, карточки товара и кассовой связи. Не создавать outbound-операций Эвотор.
7. Реализовать общий экран номенклатуры и экран «Склад», затем принять их на реальных данных отдельно.

## Явно исключенные решения

Миграция **не** объединяет автоматически одинаковые наименования между магазинами, не записывает цену или себестоимость в Эвотор, не выгружает новые реальные каталоги других точек, не создает тестовые товары и не принимает накладные или остатки из 1С. Если впоследствии понадобится объединить еще один кассовый каталог с существующим товаром, администратор сделает это отдельным явным действием с общим audit trail.
