# Автоматическая read-only синхронизация Эвотор

**Дата решения:** 18.09.2026. **Статус:** задания зарегистрированы для закрепленных и нескрытых складов; приемка выполнения продолжается.

Автоматизация сохраняет действующую архитектурную границу: работа с Cloud API V2 выполняется только сервером, токен не попадает в клиент, и никакие `POST`/`PUT`/`PATCH`/`DELETE` в Эвотор не выполняются. Обновление каталога читает номенклатуру, иерархию групп, штрихкоды, маркировочный тип и опубликованный остаток. Обновление документов читает только следующую cursor-страницу чеков и товарных строк. Фискальные идентификаторы, реквизиты оплат, адреса и технические идентификаторы касс не сохраняются в UI.

| Работа | Расписание | Обоснование |
|---|---:|---|
| Каталог, категории, маркировка, остатки | каждые 15 минут, один склад по очереди | Обход каталога ограничен пятью страницами и строго одним закрепленным складом за запуск; это укладывается в лимит callback и дает каждой точке обновление в пределах цикла сети без пакетного всплеска. |
| Чеки и товарные строки | каждые 10 минут, один склад по очереди | За запуск читается только одна cursor-страница одной закрепленной нескрытой точки. Незавершенный cursor продолжает обслуживаться до окончания, затем очередь переходит к наименее давно обработанной точке. Это ниже установленных поставщиком лимитов, которые API публикует заголовками `X-RateLimit-*`. |

Каждая задача идентифицируется непрозрачным UID managed scheduler и проверяется сервером. Запуск, результат или ошибка сохраняются в едином журнале изменений с объектом `operational_sync`; отдельного журнала не создается. Расписание можно приостановить без удаления данных. Источник лимитов: [общая информация REST API Эвотор](https://developer.evotor.ru/docs/rest_overview.html).

## Проверка исполнения

18.09.2026 подтверждено, что оба platform-managed задания включены с ритмом **15 минут** для каталога и **10 минут** для документов. Одновременно журналы платформы показали техническое ограничение фактического callback примерно 30 сек: запуск может быть отмечен timeout, хотя серверное сохранение продолжается и обновляет внутреннее состояние позже. Поэтому автоматизацию нельзя считать принятой до повторной проверки успешных запусков без timeout. Сохранение каталога и документов переработано на ограниченные параллельные DB-пакеты, чтобы один callback укладывался в наблюдаемый предел; это не меняет состав читаемых данных и не добавляет write-вызовов в Эвотор.


## Справка о типе товара для будущей выгрузки

Для read-only отображения кода типа товара используется документированное соответствие из [справочника товароучёта Эвотор](https://developer.evotor.ru/docs/doc_java_inventory.html): обычный товар — `NORMAL`, маркированный алкоголь — `ALCOHOL_MARKED`. В интерфейсе этот код служит только прозрачным ориентиром будущего контрактного слоя; какие-либо запросы записи в Эвотор по-прежнему отсутствуют. В документе также подтверждены поля маркированного алкоголя: `alcoholByVolume`, `alcoholProductKindCode`, `tareVolume` и алкокоды.
