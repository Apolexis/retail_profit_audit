# Технический контракт будущего обмена с самописной ERP (API)

> Статус: **подготовительный документ**. Реализация и подключение отложены до отдельного согласования. Финансовые факты приложения этим документом не меняются.

## 1. Назначение и границы

API предназначен для одностороннего обмена данными: самописная ERP передает операционные факты (чеки, продажи, остатки, партии, заявки, перемещения), а приложение «Аналитика „Рыбный“» нормализует их в аналитические витрины и формирует рекомендации. Первичные финансовые факты, загруженные из Excel, **не перезаписываются** и не подменяются: данные ERP пополняют отдельный операционный контур.

В аналитические полезные нагрузки **не включаются персональные данные покупателей** (ФИО, телефон, дата рождения). Контур лояльности проектируется изолированно после юридической проработки.

## 2. Аутентификация и безопасность

| Параметр | Значение |
| --- | --- |
| Транспорт | HTTPS, TLS 1.2+ |
| Аутентификация | `Authorization: Bearer <token>` (выдается приложением, хранится в секретах) |
| Идемпотентность | Обязательный заголовок `X-Idempotency-Key` (уникальный UUID события ERP) |
| Формат | `application/json`, кодировка UTF-8, даты ISO 8601 с зоной (`2026-09-14T09:00:00+03:00`) |
| Пагинация | `cursor` (прозрачный курсор, без offset-сканирования) |
| Размер пакета | До 1000 событий на запрос, общий лимит 5 МБ |
| Частота | Не чаще 1 запроса/10 с на узел ERP; массовая первичная загрузка — отдельной сессией |

Ответы ошибок унифицированы: `{"error":{"code":"string","message":"string","field":"string?"}}` с кодами `400 invalid_schema`, `401 unauthorized`, `409 duplicate_event`, `422 inconsistent_reference`, `429 rate_limited`, `500 internal`.

## 3. Ресурсы API

### 3.1 `POST /erp/v1/sales` — продажи и чеки (без ПД)

```json
{
  "events": [
    {
      "event_id": "uuid",
      "store_code": "A2",
      "sold_at": "2026-09-14T12:31:00+03:00",
      "receipt_no": "2026-09-14-A2-1123",
      "item_sku": "SMK-001",
      "item_name": "Семга копченая, 200 г",
      "quantity": 0.2,
      "unit": "kg",
      "purchase_price": 980.0,
      "sale_price": 1490.0,
      "amount": 298.0,
      "payment": "cash|cashless",
      "is_return": false
    }
  ]
}
```

Правила: `store_code` обязан существовать в справочнике магазинов приложения; `quantity > 0`; возвраты передаются с `is_return: true` и положительными количествами/суммами, знак применяется при нормализации.

### 3.2 `POST /erp/v1/stock-batches` — остатки, партии, сроки

```json
{
  "snapshots": [
    {
      "store_code": "A2",
      "item_sku": "SMK-001",
      "batch_id": "B-2026-09-01-17",
      "produced_at": "2026-09-01T00:00:00+03:00",
      "expires_at": "2026-09-20T23:59:59+03:00",
      "quantity_on_hand": 4.6,
      "unit": "kg",
      "as_of": "2026-09-14T09:00:00+03:00"
    }
  ]
}
```

Снапшоты полные на момент `as_of` по указанному магазину; приложение сравнивает покрытие запаса продажами из контура ERP.

### 3.3 `POST /erp/v1/requisitions` — заявки магазинов со склада

```json
{
  "events": [
    {
      "event_id": "uuid",
      "kind": "created|approved|shipped|received|cancelled",
      "requisition_id": "REQ-771",
      "from_code": "WAREHOUSE",
      "to_code": "A2",
      "item_sku": "SMK-001",
      "quantity": 12.0,
      "occurred_at": "2026-09-14T08:15:00+03:00"
    }
  ]
}
```

### 3.4 `POST /erp/v1/transfers` — перемещения между точками

Та же структура, что у заявок, с `from_code` и `to_code` — кодами магазинов. Перемещение, инициированное рекомендацией приложения, всегда создается как **черновик** и исполняется только после ручного подтверждения управляющего; приложение самостоятельно не отправляет команды списания/перемещения в ERP.

### 3.5 `GET /erp/v1/ack?cursor=…` — статус приема

Приложение отдает подтверждения обработки: `{"accepted":["event_id"],"rejected":[{"event_id":"…","code":"duplicate_event"}],"next_cursor":"…"}`. ERP обязана повторять только неподтвержденные события с тем же `X-Idempotency-Key`.

## 4. Сверка и контроль качества

1. Ежесуточная контрольная сумма: сумма продаж и количество строк по каждому магазину за день (`POST /erp/v1/daily-control`) — расхождение выше 0,5% или отсутствие строк блокирует построение рекомендаций за этот день.
2. Дубликаты определяются по `event_id`; повторная отправка безопасна.
3. Все отклоненные события видны в журнале приложения с причиной отклонения.

## 5. Рекомендации перемещения (будущий этап)

На основе контуров 3.1–3.2 приложение формирует рекомендацию по конкретному товару/партии, которые плохо продаются или не успеют реализоваться до истечения срока:

- объект рекомендации: `item_sku`, `batch_id`, точка-источник, количество к перемещению;
- **до трех точек-получателей**, ранжированных по фактическому спросу, скорости продаж, текущему остатку и остаточному сроку годности;
- текстовые основания выбора для каждой точки;
- решение и исполнение — только вручную, в ERP или через черновик заявки.

## 6. Что нужно от владельца ERP для запуска пилота

Подтвержденная версия ERP и документация, технический токен, тестовая выгрузка без персональных данных, словарь `store_code`/`item_sku`/`unit`, правила округления количеств и перечень событий заявок. Пилот начинается с 1–2 магазинов и одной товарной категории.
